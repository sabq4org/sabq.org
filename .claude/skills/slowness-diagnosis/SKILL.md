# تشخيص البطء العام في سبق

منهجية مستخلصة من حوادث 2026-07-14 و2026-07-18 المؤكدة. اتبع الترتيب — كل خطوة تستبعد جانيًا قبل التعمق.

## 1) النشرات أولًا

`railway deployment list` — إن كانت النشرات متقاربة (كل دمج PR ينشر تلقائيًا) فالموقع شبه دائم في إقلاع بارد: كل deploy = موجة بطء **2–4 دقائق** (تصفير كاش الذاكرة/SWR + Leader failover). 11 نشرة في ساعتين كانت كافية لشكوى «بطء دائم». لا تتهم القاعدة قبل استبعاد هذا.

## 2) pool معلّق؟ Redeploy أولًا ثم شخّص

عاصفة «Connection terminated unexpectedly» / ECONNRESET في كل الاستعلامات + حلقة reconnection كل 10 ثوانٍ لا تتعافى = pool اتصالات neon-serverless علق بعد تبديل نشرة (حدث مرتين يوم 2026-07-18). **العلاج: Redeploy من Railway** (عملية جديدة = pool نظيف)، والكود المدموج غالبًا بريء.

## 3) هل القاعدة مشغولة فعلًا؟

قارن `pg_stat_activity` مع الأعراض:
- **قاعدة خاملة + موقع بطيء** ⇒ المشكلة في عملية Node: event loop محجوب، حجم استجابات، pool — ليست القاعدة.
- **قاعدة مشغولة** ⇒ استعلامات ثقيلة (Neon compute pressure — راجع حادثة 2026-07-22).

## 4) أحجام الاستجابات

حادثة `/api/stories` المرجعية: 8.2MB JSON لكل طلب + ~2,014 استعلام count حجبت الموقع كله (أُصلحت في PR \u200E#870 بخدمة نحيفة + withSWR). ابحث عن endpoint يرجّع ميجابايتات — تطبيقات الجوال تستدعي مسارات لا يلمسها الويب.

**إثبات السببية تجريبيًا:** طلبات ثقيلة متوازية على المسار المتهم + قياس مسار خفيف في نفس الوقت.

## حقائق مضخِّمة ثابتة (لا تعيد اكتشافها)

- Cloudflare لا يكاشي استجابات API إطلاقًا (`cf-cache-status: DYNAMIC` رغم s-maxage) — كل زائر يضرب Railway مباشرة.
- `/api/auth/user` تستدعيه كل صفحة؛ له كاش 60 ثانية منذ PR \u200E#978.
- `SKIP_DB_MAINTENANCE=true` مضبوط على Railway (صيانة الإقلاع كانت جزءًا من موجة كل deploy).
- موجة قصيرة على رأس النشرة تزول خلال دقائق = cold cache طبيعي، لا تخلطها بالبطء المستمر.
