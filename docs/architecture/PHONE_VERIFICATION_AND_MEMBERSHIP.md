# توثيق الجوال وعضوية الدخول (`PHONE_VERIFICATION_AND_MEMBERSHIP`)

> آخر تحديث: 2026-09-18 | الأنظمة: `auth-rbac` (المالك) + `account-center` + `editorial`

مرجع مصاحب لـ [`AUTHENTICATION_FLOW.md`](./AUTHENTICATION_FLOW.md)، ويوثّق مسار
إضافة رقم الجوال وتوثيقه والدخول به مع الحفاظ على العضوية، وسجل التغييرات التي
نُفّذت في 2026-09-18.

---

## 1) الغرض

- تمكين العضو/المنسوب من **إضافة رقم جواله وتوثيقه** ثم **الدخول به إلى حسابه الحالي**
  مع الحفاظ على `id` ودوره وصلاحياته وبياناته.
- منع إنشاء حساب قارئ جديد للشخص نفسه، ومنع ربط رقم يملكه حساب آخر.
- التعامل الآمن مع الأرقام المتعارضة والحسابات المكرّرة **دون دمج أو حذف تلقائي**.

## 2) أين يُحفظ الرقم ومن يكتبه؟

| الحقل | الجدول | يُستخدم للدخول؟ | من يكتبه |
|-------|--------|:---:|----------|
| `phone_number` | `users` | ✅ نعم | مسار توثيق OTP (`/api/account/phone/*`)، الإدارة، نسخ جوال طلبات المنسوبين عند الاعتماد |
| `phone_verified` | `users` | يرجّح الاختيار عند التعارض | مسار التوثيق (`true`)، أو `false` عند تغيير الرقم |
| `official_phone` | `staff_profiles` | لا (يُستخدم احتياطًا للربط عند الدخول) | حقل HR في قسم «التواصل والطوارئ» |

> لا يوجد قيد `unique` على `users.phone_number`؛ التفرّد مفروض في منطق التطبيق
> (`findUsersByPhone` + `classifyPhoneConflict`)، لأن الصيغ التاريخية مختلطة.

## 3) تدفّق توثيق الجوال (ويب)

نقاط الدخول: `server/routes/phoneRegistration.ts` (محمية بـ `isAuthenticated` + CSRF
+ محدِّد `registrationLimiter`). غرض OTP مستقل: `phone_verify`
(`server/services/otpService.ts`).

```
المستخدم (مسجّل دخول)
  └─ إعدادات → الحساب → «إضافة/تغيير الرقم»  (AccountSection.tsx)
       │  أو: ملف المنسوب → الهوية → «إضافة/تغيير الرقم»  (StaffProfileForm.tsx، وضع self)
       ▼
1) POST /api/account/phone/send   { phone }
     - normalizePhone → E.164 (+9665XXXXXXXX)
     - classifyPhoneConflict(e164, me)  → تعارض؟ 409 برسالة واضحة (بلا كتابة)
     - sendOtp(e164, "phone_verify")   → 6 أرقام، 5 دقائق، 5 محاولات، 3/15د، فاصل 60ث
2) POST /api/account/phone/verify { phone, code }
     - فحص التعارض مجددًا (قبل استهلاك الرمز)
     - verifyOtp(e164, code, "phone_verify")
     - claimVerifiedAccountPhone(me, e164): قفل استشاري + إعادة فحص داخل معاملة
         ├─ تعارض منسوب آخر  → 409 (لا كتابة)
         ├─ تعارض عضوية قارئ → 409 + توجيه للدعم (لا سحب للرقم)
         └─ OK → users.phone_number = e164، phone_verified = true
     - إبطال كاش /api/auth/user
```

**قاعدة ذهبية:** لا يُحفظ الرقم ولا يُعلَّم موثّقًا إلا بعد نجاح OTP (إثبات الملكية).
الرقم نفسه يُطبّع دائمًا إلى E.164 في كل مسارات الكتابة.

## 4) الدخول بالجوال وكيف يحافظ على العضوية

- **ويب:** `POST /api/auth/phone/verify` (`server/routes.ts`) يستدعي `findExistingPhoneUser`
  **بحثًا فقط** (`server/services/phoneAuth.ts`):
  - حساب قائم → تسجيل دخول Passport بنفس الصف (id/role/permissions كما هي). مع بوابة 2FA إن كانت مفعّلة.
  - رقم جديد → `registrationRequired + registrationToken` ثم `/api/auth/phone/complete-registration`
    (إنشاء حساب قارئ جديد فقط بعد إثبات الملكية).
- **بحث الرقم** يغطي كل الصيغ: `findUsersByPhone` + `phoneMatchSql` (مقارنة بعد إزالة غير الأرقام،
  أو آخر 9 أرقام) — أي أن `05…` و`966…` و`+966…` كلها تطابق.
- **اختيار الحساب عند التعدد:** `pickPreferredPhoneUser` يرتّب: منسوب > قارئ، ثم
  `phoneVerified=true`، ثم الأقدم إنشاءً.
- **موبايل v1:** `/api/v1/auth/phone/verify` يستدعي `findOrCreatePhoneUser` الذي ينشئ سجل
  onboarding مبكرًا لرقم جديد (عقد التطبيقات يتطلب token+user مباشرة). لا يتغيّر في هذا التوثيق.

## 5) التعارض والتكرار — بلا دمج تلقائي

- `classifyPhoneConflict` / `claimVerifiedAccountPhone`: لا حذف، لا دمج، لا سحب رقم من حساب آخر.
- عند التعارض تُعاد 409 برسالة:
  - منسوب آخر: «راجع الإدارة لتسويته».
  - عضوية قارئ سابقة: «تواصل مع الدعم لتوحيد العضوية دون فقدان بياناتك».
- **إن كان الرقم على حساب قارئ ويُدخل المنسوب رقمه من الملف:** يُرفض (لا يُنقل الرقم تلقائيًا).
- **أداة تدقيق (قراءة فقط):** `scripts/report-duplicate-phones.ts`
  `npx tsx scripts/report-duplicate-phones.ts` — تسرد الأرقام المكرّرة بين الحسابات النشطة
  وصاحب الرقم لكل حساب، ليتخذ فريق الدعم قرارًا يدويًا موثّقًا.

## 6) قيود الكتابة الخام (لمنع الالتفاف)

| المسار | السلوك |
|--------|--------|
| `PATCH /api/auth/user` | **يتجاهل `phoneNumber`** — لا كتابة خام |
| `PUT /api/staff-profiles/me` (self) | **يرفض أي تغيير لرقم الجوال** (409) ويوجّه لتوثيق OTP |
| `PUT /api/staff-profiles/:userId` (إدارة) | يفحص التعارض (`classifyPhoneConflict` → 409) |
| `PATCH /api/admin/users/:id` | يفحص التعارض عبر `assertPhoneAvailable` |
| `POST /api/admin/users` | يفحص التعارض عبر `assertPhoneAvailable` |
| `PUT /api/v1/members/profile` (موبايل) | لا يقبل `phoneNumber` أصلًا |

`upsertStaffProfile` أيضًا يُسقط `phoneVerified` عند تغيير الرقم.

## 7) واجهات المستخدم

- **إعدادات → الحساب** (`client/src/pages/settings/sections/AccountSection.tsx`):
  بطاقة «رقم الجوال» تعرض الرقم وحالة التوثيق (موثّق/غير موثّق) مع تدفّق إرسال/تأكيد الرمز.
- **ملف المنسوب** (`client/src/components/staff/StaffProfileForm.tsx`، `access="self"`):
  حقل الجوال للقراءة فقط + زر «إضافة/تغيير الرقم» يفتح نفس تدفّق التوثيق. (وضع الإدارة يُبقي الحقل قابلًا للتحرير.)
- صفحة `/profile` القديمة: أُزيل حقل الجوال الخام منها.

## 8) الاختبارات

- **وحدة مُشغَّلة:** `tests/unit/accountPhoneVerification.test.ts` + `phoneAuth` + `phoneRegistration`
  + `otpService` + `effectiveRoles` — 36 اختبارًا ناجحًا.
  تغطي: تطبيع `05`/`966`/`+966`/`00966`، تصنيف صاحب الرقم (منسوب/قارئ/غير معروف)، تفضيل المنسوب، عزل أغراض OTP.
- **قبول (تحتاج DB — staging):**
  1. منسوب بلا رقم → يوثّق من ملفه → يدخل بالجوال: نفس `id`/الدور/الصلاحيات، **بلا صف جديد**.
  2. رقم يملكه حساب آخر → 409 بلا أي كتابة.
  3. تغيير الرقم من ملف المنسوب ذاتيًا → 409 ويوجّه للتوثيق.
  4. تعارض مع عضوية قارئ → لا دمج ولا حذف.

## 10) متبقيات مقترحة

- **موبايل v1:** إبقاء `findOrCreatePhoneUser` كما هو؛ يُفضّل لاحقًا إرجاع حالة «تعارض/استكمال»
  بدل إنشاء قارئ صامت لرقم موجود على منسوب.
- **حالة «الرقم على عضوية قارئ سابقة»:** تُوجّه للدعم. الخيار التالي هو **نقل مطالبة موثّق بلا حذف**
  (تفريغ الرقم من القارئ مع سجل تدقيق) بعد قرار المالك.
- **`official_phone`** (حقل HR): لا يزال قابلًا للتحرير ذاتيًا؛ ليس مسار دخول مباشرًا لكن يُستخدم
  احتياطًا في الربط عند الدخول — يُنصح بمراجعته لاحقًا.
