# تشغيل صور الأخبار على Cloudflare R2 وسياسة الكاش

> **آخر تحديث:** 2026-07-13
>
> **الحالة:** R2 يعمل فعلياً، والنطاق `media.sabq.org` في حالة `Active`. كاش السنة **لم يُفعّل بعد**.
>
> **المتابعة:** [Issue #841](https://github.com/sabq4org/sabq.org/issues/841) · [Backend PR #842](https://github.com/sabq4org/sabq.org/pull/842) · [Web PR #843](https://github.com/sabq4org/sabq.org/pull/843)

هذا الملف هو المرجع التشغيلي المعتمد لرفع صور الأخبار إلى R2، التدرج في التفعيل، سياسة الكاش، التراجع، ونقل الأرشيف لاحقاً.

## ملخص القرار

- يواصل المحرر رفع الصورة من محرر الأخبار في لوحة التحكم بالطريقة المعتادة؛ لا يوجد مسار عمل جديد للمحررين.
- يقرر الخادم داخلياً هل تُرفع صورة الخبر إلى R2 أو إلى Cloudflare Images حسب نسبة التفعيل.
- صور الأخبار الجديدة في R2 تستخدم رابطاً فريداً يحتوي UUID؛ تعديل صورة الخبر ينشئ رابطاً جديداً ولا يستبدل محتوى الرابط القديم.
- الصور الشخصية، صور الكُتّاب، الشعارات، التصنيفات، والإعلانات لا تدخل في هذا التحويل.
- لا تحتاج تطبيقات iOS أو Android إلى تحديث، لأنها تعرض رابط HTTPS الذي يعيده الـ API. يلزم اختبار نسخ الإنتاج الحالية فقط.
- الكاش الحالي يومان. الهدف بعد الاستقرار هو سنة على حافة Cloudflare، ثم سنة في المتصفح للصور التي تجاوز عمر خبرها 90 يوماً.
- أرشيف `imagedelivery.net` القديم لا ينتقل تلقائياً إلى R2؛ نقله مشروع مستقل.

رابط تحقق ناجح:

```text
https://media.sabq.org/news/2026/07/cb6842cd-0d09-4a86-92dc-9e498430fd6c/w730.webp
```

أعاد الرابط في وقت التحقق `HTTP 200` و`Content-Type: image/webp`، وكانت سياسة الكاش الحالية:

```text
Cache-Control: public, max-age=172800, s-maxage=172800, stale-while-revalidate=7200
```

أي يومان للمتصفح ويومان على حافة Cloudflare، مع ساعتين `stale-while-revalidate`.

## تدفق الرفع ونقاط الصور المشمولة

```text
محرر الأخبار / تطبيق الجوال / الوكيل التحريري
                    ↓
             API الرفع الحالي
                    ↓
         NewsImageStorageService
          ↙                    ↘
 R2 حسب نسبة التفعيل       Cloudflare Images
          ↓                    ↑
 media.sabq.org        fallback عند فشل R2
```

الخدمة تتعرف على أغراض صور الأخبار التالية:

- صور المقالات العربية والإنجليزية والأردية.
- الرفع القديم من محرر المقالات والصور المصغرة.
- الصور المولدة بالذكاء الاصطناعي داخل سياق المقال.
- رفع المقالات ومراجعاتها من مسارات الجوال.
- صور وكيل البريد ووكيل WhatsApp المرتبطة بالمقالات.

المسار الناتج يأخذ هذا الشكل:

```text
news/YYYY/MM/<uuid>/original.<ext>
news/YYYY/MM/<uuid>/w480.webp
news/YYYY/MM/<uuid>/w960.webp
news/YYYY/MM/<uuid>/w1600.webp
```

تُنشأ المقاسات التي لا تتجاوز عرض الأصل فقط. صور GIF المتحركة تُحفظ كما هي ولا تُحوّل إلى صورة ثابتة.

## متغيرات Railway

تُضاف إلى خدمة الـ API فقط، ولا تُحذف متغيرات Cloudflare Images الحالية لأنها مسار التراجع التلقائي:

```text
NEWS_IMAGES_R2_ACCOUNT_ID=<Cloudflare Account ID فقط>
NEWS_IMAGES_R2_ACCESS_KEY_ID=<R2 Access Key ID>
NEWS_IMAGES_R2_SECRET_ACCESS_KEY=<R2 Secret Access Key>
NEWS_IMAGES_R2_BUCKET_NAME=sabq-news-images
NEWS_IMAGES_R2_PUBLIC_URL=https://media.sabq.org
NEWS_IMAGES_R2_ROLLOUT_PERCENT=0
```

قواعد مهمة:

- `NEWS_IMAGES_R2_ACCOUNT_ID` هو **Account ID فقط**، وليس رابط S3 API ولا اسم الحاوية.
- `NEWS_IMAGES_R2_PUBLIC_URL=https://media.sabq.org` قيمة صحيحة.
- رمز R2 يحتاج صلاحية `Object Read & Write` على حاوية `sabq-news-images` فقط.
- لا تُحفظ المفاتيح أو التوكنات في Git أو المستندات أو السجلات.
- لا تستخدم صلاحية Admin ما دام التطبيق يحتاج قراءة/كتابة العناصر فقط.

## التدرج الآمن في التفعيل

يُغيّر `NEWS_IMAGES_R2_ROLLOUT_PERCENT` في Railway وفق الجدول التالي:

| النسبة | أقل مدة مراقبة | الانتقال للمرحلة التالية عندما |
|---:|---:|---|
| `5` | 24 ساعة | لا توجد أخطاء رفع متكررة، وروابط R2 تظهر على المنصات الثلاث |
| `25` | 12–24 ساعة | معدلات الرفع والعرض طبيعية ولا توجد زيادة في fallback |
| `50` | 12–24 ساعة | R2 مستقر والحذف والعرض يعملان |
| `100` | 24–48 ساعة | كل نقاط الرفع الرئيسية اختُبرت ولا توجد أخطاء حرجة |

بعد كل تغيير في Railway يلزم إعادة نشر خدمة الـ API إن لم تطبق المنصة المتغير تلقائياً على النسخة الجارية.

اختيار العينة ثابت بحسب مفتاح المستخدم/عملية الرفع. إذا فشل R2، يحاول الخادم Cloudflare Images تلقائياً؛ لذلك يجب إبقاء إعداد Cloudflare Images فعالاً طوال الانتقال وحتى انتهاء فترة الاستقرار.

### اختبار كل مرحلة

1. ارفع صورة جديدة من محرر الأخبار.
2. تأكد أن الرابط يبدأ بـ`https://media.sabq.org/news/` للعينة الواقعة ضمن R2.
3. افتح الخبر من الويب وiOS وAndroid.
4. تأكد من ظهور الصورة المصغرة والصورة الكبيرة.
5. راقب Railway بحثاً عن `[News Images] R2 upload failed`.
6. راقب Objects وClass A/Class B Operations داخل حاوية R2.
7. جرّب تعديل صورة خبر وتأكد أن الرابط الجديد مختلف.

## سياسة الكاش المعتمدة

### الوضع الحالي

| نوع الصورة | Browser TTL | Edge TTL | الحالة |
|---|---:|---:|---|
| صور أخبار R2 الجديدة | يومان | يومان | مفعّل الآن |
| الصور الشخصية والشعارات والتصنيفات والإعلانات | دون تغيير | دون تغيير | خارج نطاق الخطة |
| أرشيف Cloudflare Images القديم | دون تغيير | دون تغيير | لم يُنقل إلى R2 |

### الوضع المستهدف

| نوع الصورة | Browser TTL | Edge TTL | السبب |
|---|---:|---:|---|
| صورة خبر حديث، أقل من 90 يوماً | يومان | سنة | تقليل طلبات R2 مع بقاء مرونة أعلى في متصفح الزائر |
| صورة خبر قديم، 90 يوماً فأكثر | سنة + `immutable` | سنة | الرابط فريد ولا يُستبدل محتواه |
| صورة شخصية أو شعار قابل للتعديل | مدة قصيرة | مدة قصيرة/متوسطة | قد تتغير مع بقاء الرابط نفسه |

`max-age` يخص متصفح الزائر، و`s-maxage`/Edge TTL يخص شبكة Cloudflare. تنظيف كاش Cloudflare لا يمسح النسخة الموجودة داخل متصفح الزائر؛ لذلك لا يُرفع Browser TTL إلى سنة للصور الحديثة.

مراجع Cloudflare الرسمية:

- [الفرق بين Edge Cache TTL وBrowser Cache TTL](https://developers.cloudflare.com/cache/how-to/edge-browser-cache-ttl/)
- [تفعيل كاش Cloudflare أمام R2 عبر Custom Domain](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/)
- [تنظيف ملف واحد من كاش Cloudflare](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-single-file/)

## متى نفعّل كاش السنة؟

لا يُفعّل لمجرد نجاح رفع واحد. الترتيب المعتمد:

1. يصل R2 إلى `100%` ويستقر 24–48 ساعة.
2. تنجح اختبارات الرفع والعرض والتعديل والحذف على المنصات الثلاث.
3. يُنفّذ تنظيف كاش Cloudflare تلقائياً عند حذف صورة R2، ويشمل الأصل وكل المقاسات.
4. بعد نجاح اختبار الحذف والتنظيف، تُنشأ Cache Rule على:
   - Hostname يساوي `media.sabq.org`.
   - Path يبدأ بـ`/news/`.
   - Edge Cache TTL يساوي سنة (`31536000` ثانية).
   - Browser Cache TTL يحترم ترويسة الأصل، ليبقى يومين في المرحلة الأولى.
5. تُراقب Cache Analytics وطلبات R2 لمدة 48 ساعة إضافية.

سبب شرط التنظيف: الخدمة الحالية تحذف عناصر R2، لكن كاش الحافة قد يحتفظ بنسخة منها. رفع Edge TTL إلى سنة قبل ربط الحذف بـPurge قد يبقي صورة محذوفة متاحة من الكاش.

### المرحلة الثانية: سنة في متصفح الأخبار القديمة

بعد استقرار Edge TTL لمدة سنة، تُنفّذ آلية مستقلة تحول الصور التي تجاوز عمرها 90 يوماً إلى:

```text
Cache-Control: public, max-age=31536000, s-maxage=31536000, immutable
```

هذا التحويل **غير موجود في الكود حالياً**. يجب تنفيذه بآلية آلية تعتمد تاريخ `YYYY/MM` في المسار، مثل Worker مضبوط بعناية أو تحديث Metadata مجدول. لا تُدار القواعد شهرياً بصورة يدوية.

## نقل أرشيف الأخبار السابق

الصور القديمة الموجودة على `imagedelivery.net` لا توجد تلقائياً داخل `sabq-news-images`. نقلها مرحلة منفصلة بعد استقرار الرفع الجديد:

1. حصر روابط صور الأخبار فقط واستبعاد الصور الشخصية والشعارات والإعلانات.
2. نسخ الأصل إلى R2 وإنشاء المقاسات المطلوبة.
3. إنشاء مسار UUID ثابت لكل صورة.
4. تحديث مراجع قاعدة البيانات على دفعات صغيرة مع سجل rollback.
5. اختبار عينة من العربية والإنجليزية والأردية والويب والتطبيقات.
6. إبقاء المصدر القديم فعالاً حتى اكتمال التحقق.
7. تطبيق كاش السنة فقط بعد التأكد أن الروابط غير قابلة للاستبدال وأن مسار الحذف والتنظيف يعمل.

لا يُحذف أرشيف Cloudflare Images ضمن مشروع النقل إلا بقرار منفصل وبعد فترة تحقق كاملة.

## المراقبة

راقب العناصر التالية أثناء التدرج وبعد تفعيل الكاش:

- Railway Logs: أخطاء `[News Images] R2 upload failed` و`NEWS_IMAGES_R2_* is incomplete`.
- R2 Metrics: حجم الحاوية، Class A Operations، وClass B Operations.
- Cloudflare Cache Analytics: نسبة HIT/MISS على `media.sabq.org`.
- روابط الصور المخزنة: نسبة `media.sabq.org` مقابل `imagedelivery.net` للرفعات الجديدة.
- تجربة التحرير: ظهور الصورة بعد الرفع والتعديل على المنصات الثلاث.

فحص رابط واحد:

```bash
curl -I 'https://media.sabq.org/news/YYYY/MM/UUID/w960.webp'
```

المتوقع: `200`، ونوع صورة صحيح، وترويسة `Cache-Control` المعتمدة. قد تكون أول استجابة `CF-Cache-Status: MISS` ثم تصبح `HIT` لاحقاً؛ وقد تختلف النتيجة حسب مركز بيانات Cloudflare.

## الأعطال المعروفة

### `getaddrinfo ENOTFOUND sabq-news-images.https`

يعني غالباً أن قيمة `NEWS_IMAGES_R2_ACCOUNT_ID` تحتوي رابط S3 API أو اسم الحاوية بدلاً من Account ID الصافي. صحح المتغيرات بحيث يكون:

- Account ID في `NEWS_IMAGES_R2_ACCOUNT_ID`.
- اسم الحاوية في `NEWS_IMAGES_R2_BUCKET_NAME`.
- رابط العرض العام فقط في `NEWS_IMAGES_R2_PUBLIC_URL`.

ثم أعد نشر Railway واختبر بصورة جديدة.

### الرابط ما زال `imagedelivery.net`

هذا يعني أحد الآتي:

- العملية ليست ضمن نسبة التفعيل.
- الغرض ليس صورة خبر.
- إعداد R2 ناقص أو فشل الرفع، فاستُخدم fallback.

راجع Railway Logs أولاً ولا تعطل Cloudflare Images أثناء التشخيص.

## التراجع الفوري

أعد القيمة التالية ثم أعد نشر خدمة الـ API:

```text
NEWS_IMAGES_R2_ROLLOUT_PERCENT=0
```

بهذا تعود كل عمليات الرفع الجديدة إلى Cloudflare Images. روابط R2 التي رُفعت سابقاً تستمر في العمل ولا تحتاج إعادة قاعدة البيانات إلى الخلف. لا تحذف الحاوية أو النطاق عند التراجع.
