# تقرير المراجعة الشاملة لمشروع Neon — sabq.ai

> **تاريخ الفحص:** 2026-07-22  
> **مشروع Neon:** `ai sabq` (`jolly-sky-77868412`)  
> **قاعدة البيانات:** `neondb` — PostgreSQL 17.10  
> **نوع الفحص:** قراءة فقط؛ لم تُعدّل إعدادات أو بيانات أثناء المراجعة.

## الخلاصة التنفيذية

المشروع يعمل حالياً، ولا يوجد ضغط اتصالات أو جلسات محجوبة وقت الفحص. أكبر المخاطر المكتشفة هي:

1. تضخم خطير في جدول صلاحيات RBAC بسبب seed غير idempotent.
2. خرائط الموقع تمسح جدول `articles` كاملاً بصورة متكررة وتنقل ملايين الصفوف.
3. البحث الدلالي ينقل آلاف المتجهات الكبيرة من Neon إلى Node لكل طلب.
4. نقل البيانات وصل إلى نحو 1.676 TB خلال فترة الفوترة.
5. فرع الإنتاج غير محمي، ونافذة الاستعادة يوم واحد فقط.
6. بعض الاستعلامات تصل إلى 158 ثانية مع تعطيل `statement_timeout` العام.

فرع `test` لم يعد موجوداً أثناء آخر قراءة، ولذلك توقف استهلاكه المستمر. تبقى تكلفته التاريخية ضمن فترة الفوترة الحالية.

## 1. تضخم جدول `role_permissions`

### النتيجة

| المقياس | القيمة |
|---|---:|
| إجمالي الصفوف | 420,404 |
| العلاقات المختلفة فعلياً | 438 |
| الصفوف المكررة | 419,966 |
| أعلى عدد نسخ لعلاقة واحدة | 1,370 |

أكثر من 99.8% من الجدول مكرر.

### السبب

- تعريف `role_permissions` لا يفرض uniqueness على `(role_id, permission_id)` في `shared/schema.ts`.
- `onConflictDoNothing()` في `server/seedRBAC.ts` لا يمنع التكرار، لأن المفتاح الأساسي UUID جديد في كل إدخال.
- `seedRBAC()` يعمل عند كل إقلاع للإنتاج من `server/index.ts`.

كل نشر جديد يضيف مجموعة أخرى من العلاقات نفسها. الكود يزيل التكرار لاحقاً باستخدام `Set` في بعض المسارات، لكنه يجلب الصفوف المكررة من PostgreSQL أولاً ويستهلك وقتاً وذاكرة دون حاجة.

### الإجراء المقترح

1. جعل seed idempotent فعلياً.
2. أخذ نقطة استعادة قبل التنظيف.
3. تنظيف التكرارات بمعاملة أو دفعات محسوبة مع الاحتفاظ بصف واحد لكل علاقة.
4. إضافة unique index على `(role_id, permission_id)`.
5. تحديث Drizzle schema والتحقق من صفحات إدارة الأدوار والصلاحيات.

هذا التغيير يجب أن يتم كعمل Schema/Backend مستقل وفق تسلسل المشروع الآمن، وليس كتعديل مباشر مرتجل على الإنتاج.

## 2. خرائط الموقع تسبب Full Scan متكرر

### النتيجة منذ إعادة ضبط `pg_stat_statements` في 2026-07-19

- عدد الاستدعاءات: 8,980.
- الصفوف المعادة: 168,887,180.
- متوسط التنفيذ: 818.60ms.
- أقصى تنفيذ: 11.57s.
- خطة التنفيذ: `Parallel Seq Scan` على جدول `articles`.

### السبب

تقسيم الأخبار إلى 50 bucket عربية يعتمد على:

```sql
abs(hashtext(id::text)) % 50 = bucket
```

لا يستطيع PostgreSQL استخدام فهرس عادي لهذا الشرط، فيقرأ جدول الأخبار كاملاً لكل bucket. الكاش الحالي داخل ذاكرة كل عملية ولمدة 30 دقيقة، ولذلك يتكرر العمل بين نسخ التطبيق وبعد إعادة التشغيل.

### الإجراء المقترح

الخيار الأفضل هو توليد ملفات Sitemap مسبقاً وتخزينها في R2 أو Redis، وتحديثها عند النشر أو بجدول زمني. البديل هو عمود bucket محفوظ ومفهرس مع `(status, bucket, published_at)` بدلاً من حساب `hashtext` أثناء كل طلب.

## 3. البحث الدلالي ينقل المتجهات إلى Node

### النتيجة

- 689 استدعاء.
- 3.45 مليون متجه أُعيدت للتطبيق.
- متوسط التنفيذ: 6.41s.
- أقصى تنفيذ: 45.56s.

### السبب

كل طلب يجلب حتى 5,000 متجه، كل متجه 1,536 بعداً مخزناً كـ JSON، ثم يحسب cosine similarity داخل JavaScript.

### الإجراء المقترح

- تثبيت امتداد `pgvector` على فرع تجريبي أولاً.
- نقل البيانات تدريجياً إلى `vector(1536)` مع إبقاء الحقل القديم مؤقتاً.
- إنشاء HNSW أو IVFFlat index.
- تنفيذ Top-K داخل PostgreSQL وإرجاع عشرات النتائج فقط بدلاً من آلاف المتجهات.

## 4. الاستعلامات البطيئة

| النمط | المتوسط | الأقصى |
|---|---:|---:|
| البحث في عنوان الخبر | 9.81s | 47.11s |
| عد نتائج البحث بالعنوان | 4.93s | 24.14s |
| البحث في العنوان أو الملخص | 44.01s | 70.89s |
| قائمة مقالات بحثية كاملة | 33.05s | 158.20s |
| قائمة المراجعات حسب الكاتب أو المراسل | 740.80ms | 10.79s |

فهرس `idx_articles_excerpt_trgm` أصبح صالحاً عند نهاية الفحص وحجمه نحو 791 MB؛ يجب قياس الأداء بعد اكتماله قبل إضافة فهرس آخر.

إعدادات PostgreSQL الحالية:

- `statement_timeout = 0`
- `lock_timeout = 0`
- `idle_in_transaction_session_timeout = 5min`

يوصى بوضع مهلة 10–30 ثانية للاستعلامات التفاعلية، مع مهلة منفصلة للمهام الخلفية، واستخدام helper الاستعلامات المحدودة الموجود في `server/db.ts` في كل المسارات العامة الثقيلة.

## 5. مؤشرات الضغط الداخلي

منذ تشغيل Compute في 2026-06-24:

| المقياس | القيمة |
|---|---:|
| ملفات PostgreSQL المؤقتة | 48,782 |
| البيانات المؤقتة المكتوبة | نحو 1.34 TB |
| Deadlocks | 42 |
| Rollback rate | 0.015% |
| PostgreSQL cache hit | 59.7% |

لا توجد جلسات محجوبة حالياً، و`idle in transaction` عاد إلى صفر بعد ظهور حالة عابرة أثناء الفحص. يلزم الرجوع إلى Neon Monitoring وسجلات PostgreSQL/Railway لتحديد الاستعلامات المتقابلة في deadlocks.

`track_io_timing` معطل، لذلك يجب الاعتماد أيضاً على Neon LFC metrics وMonitoring لتقييم ضغط القراءة الحقيقي.

## 7. الأمان والاستعادة

### المخاطر

- `production` غير محمي في Neon.
- لا توجد IP Allowlist.
- الاتصال العام مفتوح.
- اتصالات التطبيق تستخدم غالباً `neondb_owner`، وهو دور واسع الصلاحيات يملك CREATE ROLE وCREATE DATABASE وREPLICATION وBYPASSRLS.
- نافذة PITR يوم واحد فقط.
- لم يُعثر على نسخ `pg_dump` دورية أو Snapshots موثقة في المستودع.

### التوصيات

1. تفعيل Protected Branch للإنتاج.
2. رفع PITR إلى 7 أيام على الأقل، أو أكثر حسب متطلبات الاستعادة.
3. إنشاء Snapshot دوري أو نسخة خارجية مشفرة.
4. إنشاء دور تطبيق محدود للصلاحيات اليومية، مع إبقاء `neondb_owner` للهجرات والصيانة فقط.
5. إذا كانت Railway تملك Static Egress IP، تطبيق IP Allow على الفرع المحمي فقط.
6. مراجعة كلمات المرور والاتصالات القديمة بعد نقل التطوير إلى PostgreSQL المحلي.

## 8. الاتصالات والـ Pooling

الاتصالات وقت الفحص منخفضة مقارنة بالحد:

- 24 اتصال PostgreSQL.
- أغلب اتصالات التطبيق تمر عبر PgBouncer.
- `max_connections = 4000`.
- لا توجد جلسات محجوبة.

إعداد pool في التطبيق يصل إلى 50 اتصالاً لكل نسخة، مع حد أدنى 2. الوضع الحالي صحي ولا توجد مشكلة connection saturation وقت الفحص. يجب مراقبة عدد نسخ Railway لأن الحد 50 يُضرب في عدد النسخ، مع بقاء PgBouncer هو المسار المفضل للترافيك العادي.

## 9. التخزين والجداول الأكبر

أربعة جداول تمثل نحو 85% من حجم القاعدة:

| الجدول | الحجم التقريبي |
|---|---:|
| `articles` | 7.25 GB |
| `article_daily_stats` | 5.18 GB |
| `notifications_inbox` | 2.54 GB |
| `article_ip_views` | 1.85 GB |

ملاحظات إضافية:

- `short_link_clicks`: نحو 579 MB و1.43 مليون صف.
- `image_migrations`: نحو 136 MB بإحصاءات قديمة؛ مرشح للمراجعة بعد انتهاء هجرات الصور.
- Autovacuum يعمل جيداً على أغلب الجداول الكبيرة.
- نسبة الصفوف الميتة في `articles` نحو 6.6%، وليست أزمة حالياً.
- يلزم تعريف retention واضح للإشعارات ومشاهدات IP ونقرات الروابط.
- لا يجب تشغيل `VACUUM FULL` على الجداول الكبيرة دون نافذة صيانة وتقييم القفل والمساحة المؤقتة.

## 10. نقاط إيجابية

- `test` توقف ولم يعد يضيف CU-hours.
- Autoscaling الإنتاج 2–10 CU مناسب كنطاق أولي.
- Read replica محدودة إلى 0.25–1 CU مع Scale-to-zero بعد 5 دقائق.
- لا توجد جلسات محجوبة عند نهاية الفحص.
- لا توجد فهارس invalid أو قيد البناء عند نهاية الفحص.
- معدل rollback منخفض.
- Autovacuum وAutoanalyze يعملان على الجداول الرئيسية.
- Redis مستخدم للجلسات في الإنتاج، ما يخفف ضغط PostgreSQL.

## خطة التنفيذ المقترحة

### خلال 24–48 ساعة

1. إصلاح `role_permissions` قبل أي نشر جديد.
2. تغيير الإعداد الافتراضي للـ Compute الجديد من `8–16` دائماً إلى إعداد آمن.
3. حماية فرع `production`.
4. التأكد من أن `mirror` يخدم قراءة فعلية؛ فهو Compute منفصل ومحاسب.
5. تفعيل تنبيهات الاستهلاك والحدود المالية.

### خلال أسبوع

1. إعادة تصميم توليد Sitemaps.
2. نقل البحث الدلالي إلى `pgvector` عبر migration تدريجية.
3. تطبيق مهلات على الاستعلامات التفاعلية.
4. تحليل deadlocks والاستعلامات التي تولد temp files.
5. رفع PITR وإضافة نسخة احتياطية دورية.

### خلال شهر

1. إضافة retention أو partitioning للجداول سريعة النمو.
2. فصل دور التطبيق عن دور مالك قاعدة البيانات.
3. بناء لوحة مراقبة لـ CU usage وegress وLFC hit rate وp95 query latency وdeadlocks.
