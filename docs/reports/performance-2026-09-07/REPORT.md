# تحقيق البطء المتقطع — سبق — 7 سبتمبر 2026

**النتيجة:** ثبت وجود استعلام إحصاءات مكلف، وتكرار جلب الإحصاءات عند انتهاء الكاش، وانتظار غير محدد لبيانات SEO قبل إرسال HTML. جُهزت إصلاحات محددة لهذه النقاط. لا تثبت الأدلة الحالية أنها تفسر كل نوبة بطء أبلغ عنها المستخدم، ولا يجوز إعلان تعافي الإنتاج قبل نشر الإصلاح وقياسه.

التتبع: [المشكلة #1547](https://github.com/sabq4org/sabq.org/issues/1547).

## النطاق والنسخة

- فحص النسخة المنشورة `8480337f6e3ff833dfa2a789dcd42a938b3f07db`، خدمة Railway API `3bb3702e-7ba3-4d46-8064-1882391a422b`؛ الحالة وقت الفحص SUCCESS، replica واحدة في US East. الواجهة Cloudflare Pages، وweb-next خدمة منفصلة.
- راجعت مسار Pages → API، المصادقة والجلسات، كاش البيانات، استعلامات الصفحة الرئيسية والتحرير والإحصاءات وSEO، مهام المشاهدات، والأخطاء الرياضية.
- ذكر المستخدم أن آخر اختناق كان «قبل ساعة» نحو 13:59 الرياض. النافذة المقصودة تقريبًا 12:30–13:30 الرياض (09:30–10:30 UTC). عينة التشغيل المحدودة بـ5000 سطر غطت 12:47–13:30، وليست الساعة كاملة.
- محفوظ هنا: ملخص إحصائي، خطتا SQL، ومقارنة النتائج. سجلات HTTP الخام لم تُضمّن لأنها قد تتضمن عناوين IP ومعرّفات؛ بقيت محليًا في `/tmp/sabq-perf-20260907`.
- عمل قاعدة البيانات كله قراءة فقط مع مهلات قصيرة وROLLBACK؛ لم تُغيّر متغيرات أو فهارس أو بيانات الإنتاج. الإصلاح في worktree منفصل لحماية تعديلات المستخدم الحالية.

## نتائج مؤكدة

### 1. عدّ المنشور واليوم في إحصاءات AI يختار خطة مكلفة

`server/services/aiPublicStatsService.ts` كان يجمع `count(*)` و`count(*) FILTER (WHERE published_at >= …)` تحت شرط النشر. عدد صفوف المقالات الحية المقدّر نحو مليون.

قياس `EXPLAIN (ANALYZE, BUFFERS)` للقراءة على الإنتاج:

| القياس | قبل | بعد فصل العدّ إلى استعلامين فرعيين في statement واحدة |
|---|---:|---:|
| زمن التنفيذ داخل PostgreSQL | 4216.800 ms | 117.153 ms |
| Shared hit blocks | 773910 | 952 |
| Shared read blocks | 4809 | 2088 |

الخطة القديمة استخدمت `idx_articles_sitemap_bucket`، والبديلة استخدمت `idx_articles_ai_generated` للإجمالي و`idx_articles_published_status` لليوم. الفرق ≈36 مرة في هذا القياس، **وليس وعدًا بتسريع الموقع كله بهذه النسبة**.

إعادة تحقق منفصلة داخل `REPEATABLE READ READ ONLY` أعادت في الحالتين **945213 منشورًا و42 منشور اليوم**. زمن الطلب من جهاز الفحص، شامل الشبكة، كان 547ms للقديم و334ms للجديد بعد تدفئة البيانات؛ لذلك لا تُخلط هذه الأرقام مع زمن تنفيذ EXPLAIN ولا توصف الأولى بأنها benchmark بارد مضبوط.

الأثر الظاهر: 16 طلبًا بطيئًا لـ`/api/public/ai-stats` في عينة APM، أقصاها 9739ms؛ الوسيط داخل **عينة الطلبات البطيئة فقط** 7436.5ms. الاستعلام ليس كل زمن endpoint؛ توجد تسعة استعلامات فيه.

الإصلاح: فصل العد مع الحفاظ على شرط النشر وبداية يوم الرياض وشكل JSON؛ دون فهرس جديد.

### 2. انتهاء الكاش يسمح بتكرار الاستعلامات الثقيلة

كانت الخدمات تقرأ memoryCache ثم تجلب وتحفظ، دون مشاركة الوعد الجاري:

- إحصاءات AI: 9 استعلامات لكل طلب بارد.
- إحصاءات الأخبار `/api/news/stats`: استعلامان لكل طلب بارد.
- نبض اللوحة `/api/admin/dashboard/pulse`: 8 استعلامات لكل طلب بارد.

الإصلاح: استخدام SWR القائم مع جلب واحد للطلبات المتزامنة وتقديم آخر لقطة أثناء التحديث. AI: 5 دقائق طازجة + 5 إضافية أثناء التحديث. الأخبار والنبض: دقيقتان طازجة + دقيقتان إضافيتان. يبقى `generatedAt` وقت القياس، ولا يتحول الفشل إلى أرقام مصطنعة. TTL محفوظ للجزء الطازج؛ الجديد هو نافذة التحديث الخلفي.

اختبارات 50 قارئًا متزامنًا تثبت مشاركة دفعة واحدة، والتحديث الخلفي، وثبات وقت اللقطة القديمة، والتعافي بعد فشل قاعدة البيانات. هذه حماية من تضخيم الحمل المثبت في الكود؛ لا تتوفر traces تربط عدد القراء المتزامنين أثناء كل نوبة تاريخية.

### 3. بيانات SEO تحجب HTML دون مهلة للاتصال أو قراءة الجسم

`functions/_middleware.js:cachedJson` كان ينتظر `fetch` ثم `res.text` ثم `cache.put` قبل تقديم الصفحة. الكاش البارد أو رد متعثر يجعل زيارة HTML تنتظر origin حتى لو كان ملف الواجهة جاهزًا.

الإصلاح: AbortSignal بميزانية 2500ms تشمل جسم رد origin؛ كتابة الكاش بعد التحقق من JSON عبر `context.waitUntil`؛ عند فشل جلب البيانات يعمل مسار SPA الحالي بـno-store. اختبارات تشمل تعثر headers والجسم وكتابة الكاش وJSON غير مكتمل ومسار الصفحة الكامل عند فشل SEO.

حدود التغيير: المهلة تخص جلب ميتادات/redirect من origin، وليست ميزانية لكل الصفحة أو لموارد الصور أو لجلب SSR من web-next. مهلة SSR المستقل تبقى عملًا منفصلًا. عند تعثر SEO قد تصل قشرة بلا ميتادات مخصصة مرة واحدة، ولا تُخزن كـHTML عام قابل للكاش؛ الزيارة التالية تعيد المحاولة.

## ما لا تثبته القياسات وما بقي

- **415 عينة موارد** بين 10:31 و13:58 الرياض، بفاصل 30 ثانية: `pool.waiting` دائمًا صفر؛ أكبر ذروة event-loop مسجلة 196ms. توجد عينة واحدة عند 12:47:26 فيها 50 اتصالًا مشغولًا كلها دون منتظرين. لا دليل على تشبع مستمر، لكن عينات 30 ثانية لا تنفي طوابير قصيرة بين القياسات. لا أوصي برفع pool أو تغيير حجم الخدمة عشوائيًا.
- RSS تذبذب، ولم يُثبت تسرب ذاكرة أو نفادها. لم تُؤخذ heap snapshot لأنها توقف العملية وتحتوي بيانات حساسة.
- فحص PostgreSQL اللحظي وجد 45 اتصالًا idle، ولم يرصد استعلامًا نشطًا عالقًا. إحصاءات `pg_stat_statements` تراكمية؛ `max_exec_time` التاريخي ليس دليلاً على وقت النوبة.
- **حمل المشاهدات:** مقارنة لقطتي إحصاءات خلال الفحص أظهرت 27 دمجًا بوقت SQL تراكمي ≈20.25 ثانية (≈750ms/دمج). هذا حمل متكرر مهم للتحسين اللاحق، لكن لم يثبت أنه يحجب القراءات. المشغّل `trg_articles_search` يعمل فقط عند title/subtitle/excerpt؛ لا يعيد بناء search_vector لمجرد زيادة المشاهدات. لم تُعدّل العدادات أو إسقاطاتها أو فهارسها ضمن الإصلاح.
- **الرياضة:** أخطاء API-Football تعكس cooldown وتشبع طابور المزود؛ لا تُفسر وحدها بطء لوحة التحرير. البث SSE طويل بطبيعته؛ استُبعد من مقارنة أزمنة قراءة الصفحات. كذلك لا تُعامل رسائل دمج المشاهدات الناجح كأخطاء لمجرد مستوى السجل.
- **استعلامات أخرى ثقيلة:** إحصاءات فئات الأخبار/اللوحة وملفات المراسل لها أزمنة SQL مرتفعة. فهرس reporter_id غير موجود ضمن فهارس articles التي جرى فحصها، لكن اقتراحه يحتاج خطة EXPLAIN ممثلة للبيانات واختبارًا منفصلًا، لا تطبيقًا تخمينيًا على الإنتاج.
- موصلات Railway/Neon في التطبيق كانت مرتبطة بمشروع آخر؛ استُخدمت هوية Railway CLI المرتبطة بسبق واتصال قاعدة البيانات من الخدمة نفسها. لا أسرار داخل التقرير.
- استعلامات HTTP التاريخية المحددة بالمسار والوقت أخفقت في Railway بعبارة عامة؛ متاح سجل APM في النافذة وعينات HTTP الحديثة. لا يوجد HAR من جلسة المستخدم أثناء الحادثة ولا قياس RUM يربط واجهته بمسار واحد. لهذا يبقى إسناد الاختناق الكامل غير محسوم.

## التحقق والتطبيق

- 39 اختبارًا ناجحًا في خمسة ملفات (التزامن، SWR، مهلات الميتادات، وسمات اللغة).
- بناء الخادم ناجح. TypeScript `npm run check` ناجح. ESLint للملفات المدعومة: صفر أخطاء، مع تحذيرات legacy في routes.ts؛ JavaScript/الاختبارات تتجاهلها إعدادات ESLint الحالية، وتغطيها اختبارات التنفيذ.
- لا تغييرات واجهة بصرية أو Schema أو صلاحيات أو عقود موبايل. لم يُدع اختبار شاشة محرر موثقة على الإنتاج.
- بعد اعتماد النشر: انتظار CI ونجاح نشر API وPages للـSHA الصحيح، ثم قياس `/api/public/ai-stats` و`/api/news/stats` و`/api/admin/dashboard/pulse` على عبور TTL، والتحقق من الصفحة العامة والتحرير بحساب مخول. تبقى #1547 مفتوحة حتى اختبار ذلك ومقارنة فترة تشغيل مماثلة.
