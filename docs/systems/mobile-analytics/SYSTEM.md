# قياس التطبيقات الأصلية (`mobile-analytics`)

> آخر مراجعة: 2026-09-13 | المالك: فريق المنصة

## الغرض
قياس استخدام تطبيق سبق على iOS وأندرويد بعقد أحداث متطابق، باستخدام Firebase Analytics وتدفقات التطبيقات الأصلية، بعد موافقة المستخدم. يتتبع العمل Issue #1652.

## الحدود
- داخل النطاق: واجهة SabqAnalytics، التهيئة والموافقة، أحداث الشاشات العامة والتحويلات والتفاعل والقراءة، إعدادات SDK والاختبارات.
- خارج النطاق: قياس الويب، عدادات Article/Behavior الداخلية، تطبيق VARA، الإعلانات وGTM، آليات المصادقة وFCM نفسها، نشر المتاجر وتغيير بيانات الأعضاء.

## نقاط الدخول
| الطبقة | المسار |
|---|---|
| iOS | `sabq app ios/sabq/Services/SabqAnalytics.swift` ومواضع استدعائه في Screens/Stores/ContentView |
| Android | `android-native/app/src/main/kotlin/com/sabq/smart/data/analytics/` ومواضع استدعائه في feature/SabqApp/SabqApplication |
| التهيئة | مشروع Xcode وInfo.plist وملفات Firebase العامة، وGradle وAndroidManifest |
| الخادم/البيانات | لا تغيير API أو Schema في هذا الإصلاح |

## عقود مهمة
- Firebase Analytics هو مرسل الأحداث الوحيد في النسخ الجديدة؛ لا Measurement Protocol أو api_secret أو client_id مصطنع داخل الحزمة.
- تهيئة SDK لا تعني الموافقة. analytics collection مغلق افتراضيًا قبل التهيئة حتى اختيار السماح؛ الرفض/السحب يغلق الجمع ويمسح user_id؛ الإعلانات تظل denied.
- debug لا يجمع افتراضيًا؛ تشغيل DebugView يتطلب تفعيلًا اختباريًا صريحًا. Firebase config يجب أن يطابق التطبيق والبيئة؛ لا قيم وهمية أو fallback إلى تدفق Web.
- screen_view يصف انتقالًا إلى شاشة عامة ويستبعد الإدارة/الحسابات الحساسة. مالك واحد يمنع تكرار automatic/manual.
- login بعد نجاح المصادقة؛ sign_up بعد نجاح إنشاء الحساب؛ لا تحويل عند الضغط أو الفشل. الاختيار الاشتراكي للموافقة لا يعيد إرسال أحداث سبقت الاختيار.
- search بعد نجاح استجابة مطابقة؛ لا نص بحث شخصي أو URL/secret خام. أسماء الأحداث والمعلمات محددة وصالحة، ومعرّف العضو الداخلي فقط حيث تسمح الموافقة، لا بريد/هاتف/اسم عضو.
- share_intent يعني فتح نافذة المشاركة، share يعني إتمام iOS المؤكد أو اختيار وجهة Android مع معامل stage واضح؛ لا ادعاء بنشر خارجي لا يمكن إثباته.
- push_open لا يحدث إلا من callback إشعار؛ deep_link_open مستقل للرابط المباشر، دون token أو query حساس.
- reading_time يقيس foreground الفعلي بالثواني؛ scroll_depth 25/50/75/90 مرة لكل حد في الزيارة. لا تكتب engagement_time_msec يدويًا، ولا تخلط BehaviorTracker/عدادات الخادم مع GA4.
- لا حذف للتدفقات القديمة ولا تدوير MP secrets تلقائيًا أثناء هذا التنفيذ؛ خطة انتقال النسخ القديمة موثقة قبل الإلغاء.

## صحة وتشغيل
اختبارات unit للحالات والخصوصية والجلسة، بناء iOS/Android، فحص الحزم ضد وجود سر MP، وتجربة التنقل والبحث والمشاركة والخلفية. إثبات التسجيل عبر DebugView للتدفق الأصلي ثم التقارير بعد المعالجة؛ وجود ID أو طلب وحده غير كافٍ.
