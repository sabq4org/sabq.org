# الإشعارات الفورية (`push-notifications`)

> آخر مراجعة: 2026-09-19 | المالك: platform

## الغرض
إرسال إشعارات عبر FCM / APNs / Expo مع عامل خلفي وناقل داخلي.

## الحدود
- **داخل النطاق:** خدمات الدفع، `pushWorker`, `notificationBus`, مسارات الإدارة.
- **خارج النطاق:** إشعارات البريد/SMS (قنوات أخرى).

## نقاط الدخول
| الطبقة | المسار |
|--------|--------|
| Backend | `fcm*`, `apnsService`, `expoService`, `pushWorker`, `notificationBus` |
| Android VARA | `android-native/vara/src/main/kotlin/com/sabq/vara/push/` |
| Android SABQ | `android-native/app/src/main/kotlin/com/sabq/smart/data/push/` |
| Docs | `docs/APPLE_PUSH_SETUP.md` |

## عقود مهمة / Gotchas
- `APNS_KEY_ID` / `APNS_TEAM_ID` env-only — غيابها يعطّل APNs مع تحذير إقلاع.
- Leader election يضمن عامل دفع واحد فقط.
- VARA يسجل FCM عبر `/api/v1/devices/register` بعد جلسة Bearer فقط، ويحل `sabqsports://match/:id`. تذكيرات المتابعة المحلية تستخدم `AlarmManager.setAndAllowWhileIdle` بلا صلاحية المنبه الدقيق.
- **استعادة بعد الإقلاع (2026-07-29):** `MatchReminderBootReceiver` يستمع لـ `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` ويعيد الجدولة من `followed_fixtures`؛ كذلك `VaraApplication.onCreate` يستدعي `rescheduleAll` عند كل إقلاع بارد.
- **التذكير المحلي واحد فقط: «قبل ١٠ دقائق»** — إشعار «انطلقت المباراة» يأتي من الخادم حصريًا (قرار 2026-07-04 في iOS)؛ أُزيل المحلي المزدوج من Android في 2026-07-27 لأنه كان يزدوج ويكذب عند تأخر الصافرة.
- **حزمة debug (2026-07-29):** `sportsAlertsService` يقبل `com.sabq.sports.dev` بجانب الإنتاج — ضروري لاختبار المحاكي يوم المباراة بعد نشر Railway.
- **فلتر الروابط العميقة في Manifest مفصول** (2026-07-27): دمج `sabqsports://` و`sabq://roshn` في `intent-filter` واحد كان يوحّد السمات فيشترط host على كليهما ويعطّل كل روابط `sabqsports://` الخارجية. لا تعد دمجهما.
- **FCM لتطبيق VARA مفعّل (2026-07-27):** مشروع Firebase `sabq-vara` بالحزمتين (`com.sabq.sports` + `.dev`) وبصمات SHA لمفتاحي الرفع وDebug. `google-services.json` موجود محليًا في `vara/` وغير ملتزم (gitignored — أضِفه كسرّ في CI). **البلجن يُطبَّق شرطيًا** عند وجود الملف؛ غيابه = بناء أخضر بتدهور آمن. تحقق: توكن FCM يصدر ويُسجَّل عبر `/api/v1/devices/register`.
- **فصل مشروعَي Android (2026-09-14):** تبقى `FCM_PROJECT_ID` / `FCM_CLIENT_EMAIL` / `FCM_PRIVATE_KEY` لمشروع VARA وللتوكنات القديمة غير الموسومة. تستخدم حزم سبق `com.sabqorg.sabq` و`.dev` الاعتمادات المنفصلة `FCM_SABQ_PROJECT_ID` / `FCM_SABQ_CLIENT_EMAIL` / `FCM_SABQ_PRIVATE_KEY`. لا يرجع توكن سبق إلى اعتماد VARA عند غياب إعداد سبق، حتى لا يُعطّل بسبب `SENDER_ID_MISMATCH`.
- تطبيق سبق يرسل `BuildConfig.APPLICATION_ID` مع `/api/v1/devices/register`. التوكنات القديمة بلا `bundleId` تبقى على المسار القديم تدريجيًا، ولا تُحذف أو تُعاد نسبتها بالتخمين.
- **إشعار «انتهت المباراة» (2026-08-21):** `sportsAlertsService` لا يُعلن النهاية من ومضة FT عند الاستراحة/د47 ولا عند د87 والشوط الثاني جارٍ. الحارس في `sportsMatchStatus.ts` — المصدر الحيّ يغلب، والنهاية تتطلب ≥90 دقيقة لعب و≥120 دقيقة تقويمية. Live Activity تستخدم الحارس نفسه حتى لا تُثبَّت شاشة القفل على «انتهت» أثناء الشوط الثاني.

## صحة وتشغيل
- راقب طابور العامل وسجلات الفشل
- لا استهلاك AI

## حماية بث العاجل — 2026-09-19
- `quick-send` والعامل المجدول يتشاركان حجز حملة واحدة داخل عملية API عبر `pushBroadcastCoordinator`. الطلب المتزامن الثاني يُرفض429 مع Retry-After قبل تحميل قائمة الأجهزة/إنشاء الحملة/رد202. رفض السعة لا يعني قبول الحملة أو وضعها في طابور؛ على المحرر إعادة المحاولة. الحملة المجدولة تبقى scheduled عند انشغال الحجز، ودورة العامل لا تتداخل مع نفسها. المطالبة بالحملة المجدولة ذرية عبر UPDATE مشروط ببقاء status='scheduled'، فلا ترسل نسختان الحملة نفسها.
- دفعات APNs تعمل بتزامن100 كالمسار السابق، دون انتظار أو معدل إرسال مصطنع افتراضيًا؛ أزيل أيضًا انتظار100ms القديم بين الدفعات. `pushBroadcastPacer` يسمح بتحديد معدل اختياري فقط عبر `PUSH_BROADCAST_MAX_PER_SECOND`، ويمكن تخفيض التزامن عبر `PUSH_BROADCAST_MAX_CONCURRENT`. تأخير توزيع العاجل لتخفيف القراء ليس استراتيجية مقبولة؛ الحماية تُوجّه لمسار القراءة. لا اتصالDB محجوز أثناء الانتظار؛ كتابة أحداث كل دفعة تبقى مجمعة. إشعارات Live Activity الفردية لا تدخل طابور الحملة.
- لا يوجد حد أدنى مقصود لزمن بث38ألف جهاز؛ زمن التسليم الفعلي يحتاج قياسًا، وقبولAPNs لا يثبت وصول الهاتف. حجز البث داخل العملية؛ لا طابور دائم ولا عامل منفصل ولا حد موزّع بين نسخ متعددة، وإعادة التشغيل لا تستأنف الحملة تلقائيًا. لا توسّع replicas قبل معالجة هذه الحدود.
- `httpPressure` يضيف لسجلRuntime أعداد اتصالاتHTTP الواردة والطلبات الجارية واتصالاتSSE الرياضية الجارية؛ عداد sockets الإجمالي وحده لا يثبت أنAPNs مصدر الضغط. الأرقام مجمعة بلا عناوين/IP أو رموز أجهزة.
- لا تعديل للمستلمين أو مزود تسجيل الأجهزة ضمن هذه الحماية. اختبارات `pushBroadcast*.test.ts` تستعمل DB وناقلًا وهميين؛ لا إشعار حقيقي للمشتركين.

## تشغيل الحملات — مراجعة 2026-09-05
- التسجيل مرة واحدة لكل replica، وفحص القيادة قبل الدورة والطلب الخارجي. المطالبة `scheduled → sending` ذرية.
- الفحص كل 15 ثانية. إرسال «الآن» لا يعيد حملة بدأ إرسالها أو اكتملت؛ تعديل الحملة مشروط أيضًا بالحالة.
- تسجَّل محاولة المزود قبل الإرسال ونتيجتها وعدّاداتها بعده في `push_campaign_events`. لا تُسجّل توكنات الأجهزة أو نصوص الرسائل في السجل الجديد.
- حملة sending المتوقفة 30 دقيقة تصبح `delivery_unknown` للمراجعة. لا إعادة آلية ولا ادعاء exactly-once؛ انقطاع الشبكة بعد التسليم وقبل التأكيد يظل حالة غير مؤكدة.
- حذف حملة `sending` أو `delivery_unknown` مرفوض بـ409 لحفظ سجل التسليم إلى حين حسم حالته.
