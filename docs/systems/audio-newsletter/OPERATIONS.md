# تشغيل النشرات البريدية

> آخر تحديث: 2026-09-24 — [عقد المنتج وقبول الإطلاق](NEWSLETTER_PRODUCT.md)

## الحالة التشغيلية

الإرسال الجماهيري متوقف. هذه الوثيقة تصف مسار الكود الجديد؛ لا تثبت نشره أو وصول بريد فعلي. تبقى القيمتان الآتيتان `false` في الإنتاج إلى قرار الإطلاق بعد اختبارات التسليم:

```env
ENABLE_NEWSLETTER_SCHEDULER=false
ENABLE_NEWSLETTER_DELIVERY_WORKER=false
```

لا يكفي إيقاف واحدة منهما. لا تُشغّل الطابور القديم لإطلاق «سبق في ٣ دقائق»؛ الإرسال الجديد من MailerLite بعد المراجعة.

## المعمارية

```text
اشتراك عام → انتظار تأكيد البريد → POST تأكيد صريح → مزامنة مجموعة MailerLite
مقالات منشورة → مسودة AI → محرر يراجع ويعدّل → اعتماد نسخة محددة
                                               ↓
                                   تصدير HTML وmanifest
                                               ↓
                                   إعداد واختبار MailerLite
```

- لوحة `/dashboard/newsletter-analytics` تجمع المسودات ومسار مراجعتها مع التحليلات التاريخية. الإحصاءات التاريخية ليست تقارير حملات MailerLite الجديدة.
- المجدول في Worker مستقل يجهّز مسودات فقط. لا يسجل مهمة إرسال تلقائية للمسودة.
- API لا يشغّل المجدول، ويظل `RUN_NEWSLETTER_SCHEDULER_IN_WEB=false`.
- الطابور الدائم القديم محفوظ. المسودات غير المنشورة ومسودات المنتج التحريري الجديد غير مؤهلة للتسليم منه، مع سبب منع مسجل.
- تعديل محتوى المسودة يبطل الاعتماد السابق. النسخة المصدرة تحتاج اعتمادًا مطابقًا ومصادر ما زالت مؤهلة.
- HTML المصدّر لا يعني إنشاء حملة على MailerLite أو جدولتها أو إرسالها.

## إعداد الخدمة

خدمة Railway المستقلة تستخدم `/railway.newsletter-worker.json` وأمر `node dist/newsletter-worker.js` مع health path `/health`. لا تغيّر متغيرات الإنتاج لمجرد نشر PR.

مزامنة الوتيرة تستخدم مجموعتين منفصلتين في حساب MailerLite المعتمد:

```env
MAILERLITE_DAILY_GROUP_ID=<معرف مجموعة الإصدار اليومي>
MAILERLITE_WEEKLY_GROUP_ID=<معرف مجموعة الإصدار الأسبوعي>
```

تُضبط القيم في إدارة أسرار البيئة بعد إنشاء المجموعتين والتحقق من معرفاتهما. لا تحفظ مفاتيح المزود أو عناوين المشتركين في المستودع أو السجلات. غياب الإعداد أو تعثر المزود لا يثبت اكتمال المزامنة. لا تختَر «كل المشتركين» عند إعداد حملة؛ اختر المجموعة المطابقة لوتيرتها.

رسالة تأكيد الملكية تستخدم مزود البريد الخدمي القائم. رابط التأكيد `https://sabq.org/newsletter#confirm=...` محدود الصلاحية، وفتح الرابط لا يفعّل الاشتراك. يجب التحقق من From/Reply-To وقبول المزود ووصول الرسالة إلى صندوق الفريق قبل إطلاق النموذج للجمهور.

## قبل أول حملة

1. انشر Backend أولًا ثم واجهة الجمهور والتحرير. اختبر مسار التأكيد والتفضيلات ومزامنة المجموعتين.
2. راجع حالة الطابور القديم دون حذفه أو تشغيله. لا تحمل الاشتراكات التاريخية إلى الجمهور الجديد على أساس `verifiedAt` وحده؛ كان يُملأ تلقائيًا في المسار السابق. إذا طلب صاحب عنوان تاريخي غير موسوم الاشتراك مجددًا، يجب أن يمر بطلب opt-in جديد ورسالة DOI؛ لا تُعدّل الصفوف النشطة المؤكدة ولا تعاود تفعيل الحالات النهائية.
3. يراجع المحرر المسودة وروابط مصادرها وملخصاتها ثم يعتمدها. أي تعديل لاحق يتطلب اعتمادًا جديدًا.
4. استورد HTML المعتمد في MailerLite. تحقق من التذييل القانوني وعنوان الشركة الحقيقي والمرسل وروابط التفضيلات وإلغاء الاشتراك. لا تعتمد قيمًا وهمية أو عناوين نموذجية.
5. نفّذ تجربة محصورة بصناديق الفريق وأثبت الوصول وRTL والروابط وإلغاء الاشتراك وتوقف الإرسال بعده.
6. إطلاق الحملة للجمهور خطوة تشغيلية مستقلة بعد القبول؛ تصدير الملف وحده لا ينفذها.

## التوقف والاسترداد

- أوقف/ألغِ الحملة المجدولة من MailerLite. إيقاف Worker في سبق لا يوقف حملة جدولت في المزود.
- أبقِ علمي Worker أعلاه `false`. لا تنقل الإرسال إلى MailerSend أو SendGrid كحل احتياطي للحملات.
- لا تحذف `newsletter_delivery_jobs` أو `newsletter_delivery_recipients`؛ تحفظ checkpoints التاريخية وحالات sent/failed/skipped.
- راقب حالات تأكيد الملكية، أخطاء مزامنة MailerLite، ردود webhook غير الناجحة، وعناوين منع الإرسال دون كشفها في logs.
- تحقق من عدم وجود حملتين للنسخة نفسها داخل المزود قبل إعادة أي محاولة يدوية.

لا يحتاج المنتج الجديد migration. لا تُشغّل `db:push` على الإنتاج. تبقى إجراءات أي تغيير Schema لاحق محكومة بدليل النشر.
