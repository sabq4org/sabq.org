# مقترح: تذكيرات أحداث المقالات (Article Event Reminders)

> الحالة: **مقترح — بانتظار الموافقة قبل التنفيذ**  
> التاريخ: 2026-07-31  
> المنصات: Web + iOS + Android (parity وظيفي؛ UI الويب مستقل)  
> الأنظمة ذات الصلة: `calendar` (تحريري)، `push-notifications`، متابعة القصص `story_follows`، متابعة المباريات `sports_follows`

---

## 1) المشكلة

كثير من الأخبار تتحدث عن **حدث قادم بتاريخ واضح**:

| مثال | تاريخ الحدث |
|------|-------------|
| كسوف كلي تشهده مصر والسعودية | 2 أغسطس 2027 |
| قانون/قرار يدخل حيّز التنفيذ | بعد 45 يوماً / تاريخ محدد |
| مباراة أو فعالية كبرى | تاريخ وساعة |

اليوم المقال يُنشر ويُنسى. القارئ الذي يهتم بالحدث لا يملك طريقة سهلة لطلب: «ذكّرني قبل الموعد».

---

## 2) الهدف (تجربة القارئ)

1. أثناء قراءة المقال يظهر **تنبيه واضح** إن كان الخبر عن حدث قادم.
2. زر واحد: **«ذكّرني» / «متابعة الحدث»**.
3. عند اقتراب الموعد يصل تنبيه داخل الصحيفة (In-App) و/أو Push:
   - «الحدث الذي تتابعه: كسوف أغسطس 2027 — متوقع خلال أسبوع»
   - ثم «غداً» / «اليوم»
4. الضغط على التنبيه يعيد القارئ للمقال (أو لصفحة الحدث إن وُجدت).

---

## 3) ما يوجد اليوم (ولماذا لا يكفي وحده)

| الموجود | دوره | الفجوة |
|---------|------|--------|
| `calendar` + `calendar_reminders` | تقويم **تحريري داخلي** (محررين) | تذكيرات عامة وليست per-user؛ لا ربط دائم بمقال؛ job التذكير غير مفعّل فعلياً في الإنتاج |
| `world_days` + تذكيرات | أيام عالمية تحريرية | لا إرسال حقيقي للقارئ؛ ليست على صفحة المقال |
| `FollowStoryButton` / `story_follows` | متابعة **تحديثات القصة** | ليست مرتبطة بتاريخ حدث |
| `sports_follows` + تذكير مباراة | أقرب نموذج عامل (تابع → أُبلَّغ) | خاص بالرياضة فقط |
| `push-notifications` | البنية التحتية للإرسال | جاهزة لإعادة الاستخدام |

**الخلاصة:** نحتاج نظاماً جديداً خفيفاً موجّهاً للقارئ، يعيد استخدام قنوات الإشعار ومتابعة-الـopt-in، **دون خلطه مع التقويم التحريري**.

---

## 4) المقترح المختصر

نظام اسمه المقترح: **«أحداث المقال» (Article Anchored Events)**

```
محرر / AI يستخرج تاريخ الحدث من المقال
        ↓
يُحفظ كـ "حدث مرتبط بالمقال" (تاريخ + عنوان قصير)
        ↓
قارئ يرى شريط تنبيه جميل على المقال → يضغط «ذكّرني»
        ↓
اشتراك per-user مع نوافذ تذكير افتراضية (مثلاً: 7 أيام، 1 يوم، يوم الحدث)
        ↓
Job يومي يرسل In-App + Push عبر البنية الحالية
```

---

## 5) نموذج البيانات (مقترح)

### 5.1 جدول `article_anchored_events` (حدث مرتبط بمقال)

| الحقل | المعنى |
|-------|--------|
| `id` | معرف |
| `articleId` | المقال المصدر (FK) — إلزامي |
| `title` | عنوان قصير للحدث («كسوف كلي — أغسطس 2027») |
| `eventAt` | تاريخ/وقت الحدث (timestamptz) |
| `timezone` | افتراضي `Asia/Riyadh` |
| `precision` | `day` \| `datetime` — هل الساعة معروفة؟ |
| `status` | `draft` \| `published` \| `cancelled` \| `passed` |
| `source` | `manual` \| `ai_extract` \| `calendar_link` |
| `calendarEventId` | اختياري — ربط بحدث تقويم تحريري إن وُجد |
| `createdById` / timestamps | تدقيق |

**قاعدة:** مقال واحد قد يرتبط بأكثر من حدث (نادر)، لكن الـ MVP: **حدث واحد بارز لكل مقال**.

### 5.2 جدول `user_event_follows` (اشتراك القارئ)

| الحقل | المعنى |
|-------|--------|
| `userId` + `eventId` | فريد معاً |
| `channels` | `inapp` / `push` (مثل `story_follows`) |
| `remindOffsets` | مصفوفة أيام قبل الحدث — افتراضي `[7, 1, 0]` |
| `enabled` | قابل للإلغاء |
| `lastNotifiedOffset` | لمنع التكرار |

### 5.3 لماذا لا نوسّع `calendar_events` فقط؟

التقويم التحريري موجّه لغرفة الأخبار (أهمية، مهام، AI drafts). خلط اشتراكات القرّاء فيه يعقّد الصلاحيات والعقود.  
الربط الاختياري عبر `calendarEventId` يكفي عندما يريد المحرر إعادة استخدام حدث موجود.

## 6) من يملأ تاريخ الحدث؟ (ثلاث طبقات — متدرجة)

### المرحلة أ — يدوي من المحرر (الأوثق، MVP)

في محرر المقال (أو لوحة جانبية):

- حقل: **«هل هذا خبر عن حدث قادم؟»**
- إن نعم: عنوان الحدث + التاريخ (+ وقت اختياري)
- يظهر للقارئ فقط إذا `status=published` والمقال منشور

### المرحلة ب — اقتراح AI عند الحفظ

- بعد الحفظ: خدمة خفيفة تستخرج من العنوان/المتن: «هل يوجد تاريخ حدث مستقبلي؟»
- يقترح على المحرر للموافقة — **لا يُنشر للقارئ تلقائياً** (لتجنب تواريخ خاطئة مثل «بعد سنة من الآن» بلا تحقق)

### المرحلة ج — ربط بتقويم تحريري / أيام عالمية

- إن وُجد حدث تقويم مطابق، المحرر يربطه بضغطة
- يستفيد من تاريخ التقويم دون تكرار

---

## 7) واجهة القارئ

### 7.1 شريط على صفحة المقال (واضح وغير مزعج)

يظهر تحت العنوان أو بعد المقدمة عندما يوجد حدث منشور مرتبط:

```
┌─────────────────────────────────────────────────────┐
│  📅  حدث قادم · 2 أغسطس 2027                        │
│  كسوف كلي تشهده مصر والسعودية                        │
│  متبقّي: سنة و يومين          [  ذكّرني  ]          │
└─────────────────────────────────────────────────────┘
```

بعد الاشتراك يتحول الزر إلى: **«متابَع · إدارة»** مع إمكانية الإلغاء أو تعديل النوافذ.

**مبادئ UI (ويب):** يتبع نظام تصميم الويب الحالي؛ ليس بطاقة بطبقات ظلال؛ شريط واحد واضح.  
**موبايل:** نفس المعلومة والـ CTA — يطابق iOS ثم Android 1:1.

### 7.2 صندوق «أحداثك القادمة» (اختياري لاحقاً)

- في مركز الإشعارات / صفحة «متابعاتي» بجانب متابعة القصص
- قائمة: الحدث · التاريخ · العد التنازلي · رابط المقال

### 7.3 نص التنبيه عند الاقتراب

قوالب عربية بسيطة حسب البعد الزمني:

| البعد | مثال النص |
|-------|-----------|
| ≥ 7 أيام (نافذة 7) | «تذكير: «كسوف أغسطس 2027» بعد أسبوع — المقال الذي تابعتَه» |
| غداً | «غداً: الحدث الذي تتابعه «…»» |
| اليوم | «اليوم: «…» — لا تفوّت التغطية» |

Deep link: `/article/{slug}` (ويب) و`sabq://article/{id}` (موبايل).

## 8) الإرسال (كيف يصل التنبيه)

### Job يومي (موصى به) + فحص أدق كل ساعة للأحداث ذات الساعة

1. Leader election (نفس نمط باقي الـ jobs).
2. لكل اشتراك نشط: احسب `daysUntil = eventAt - now` (بتوقيت الحدث).
3. إن طابق أحد `remindOffsets` ولم يُرسل من قبل لنفس الـ offset → أرسل.
4. القنوات:
   - **In-App:** `notifications_inbox` + `notificationBus` (يفتح مع دخول الصحيفة)
   - **Push:** عبر أجهزة `push_devices` بنفس مسار التنبيهات الرياضية

**لا نعتمد على تذكير محلي فقط في الـ MVP** (AlarmManager/UNNotification) — الخادم هو مصدر الحقيقة؛ المحلي تحسين لاحق للموبايل إن لزم.

بعد مرور `eventAt` بيوم: `status → passed` وإيقاف الاشتراكات بهدوء.

## 9) المصادقة والمنصات

| المنصة | Auth | Endpoint مقترح |
|--------|------|----------------|
| ويب | Passport session | `POST/DELETE /api/article-events/:id/follow` |
| موبايل | Bearer `/api/v1` | `POST/DELETE /api/v1/article-events/:id/follow` |
| قراءة عامة | عام | الحدث يظهر في payload المقال إن وُجد |

الزائر غير المسجّل: الزر يطلب تسجيل الدخول (نفس سلوك متابعة القصة).

## 10) ماذا عن الرياضة والقوانين والمباريات؟

| النوع | التوصية |
|-------|---------|
| خبر عام بتاريخ (كسوف، قانون، مناسبة) | **هذا النظام** |
| مباراة ضمن محرك الرياضة/VARA | يبقى على `sports_follows` — لا نكرره هنا |
| يوم عالمي تحريري بلا مقال | يبقى `world_days`؛ إن نُشر مقال يُربط عبر `calendarEventId` أو إنشاء حدث مقال يدوياً |

## 11) خطة تنفيذ مقترحة (بعد الموافقة)

حسب `AGENTS.md` — Workflow A:

| المرحلة | المحتوى | PR |
|---------|---------|-----|
| **0 — Spec** | هذا المستند + Umbrella Issue | — |
| **1 — Schema + Backend** | الجداول + CRUD للمحرر + follow APIs + job الإرسال | PR منفصل ينشر على Railway أولاً |
| **2 — لوحة المحرر** | حقول الحدث في محرر المقال / لوحة جانبية | Web dashboard |
| **3 — iOS** | شريط الحدث + ذكّرني + استقبال الإشعار | مرجع بصري لأندرويد |
| **4 — Android** | parity 1:1 مع iOS | |
| **5 — Web القارئ** | الشريط على `ArticleDetail` + قائمة متابعات | تصميم ويب مستقل |
| **6 — AI اقتراح (اختياري)** | استخراج تاريخ للموافقة البشرية | بعد استقرار اليدوي |

### نطاق الـ MVP (أول إصدار يشحن)

- إدخال يدوي للتاريخ من المحرر فقط  
- حدث واحد لكل مقال  
- نوافذ تذكير ثابتة: 7 أيام / يوم واحد / يوم الحدث  
- In-App + Push  
- ويب قارئ + API موبايل (حتى لو UI الموبايل يلحق مباشرة بعد الباكند)

### خارج الـ MVP (لاحقاً)

- اقتراح AI  
- تذكير محلي على الجهاز  
- عدة أحداث لكل مقال  
- تخصيص نوافذ التذكير من القارئ  
- ويدجت «أحداثك» في الصفحة الرئيسية

## 12) مخاطر وضوابط

| خطر | التخفيف |
|-----|---------|
| تاريخ خاطئ من AI | موافقة محرر إلزامية قبل الظهور |
| إزعاج إشعارات | افتراضي 3 نوافذ كحد أقصى؛ إلغاء سهل؛ احترام إعدادات الإشعار العامة |
| خلط مع التقويم التحريري | نظام جداول منفصل + ربط اختياري فقط |
| مقالات قديمة عن أحداث مضت | لا يظهر الشريط إذا `eventAt < now` أو `status=passed` |
| تكرار الإرسال | `lastNotifiedOffset` + idempotency في الـ job |

## 13) قرار مطلوب منك قبل التنفيذ

1. **هل نبدأ بالـ MVP اليدوي** (محرر يدخل التاريخ) أم تنتظرون طبقة AI من اليوم الأول؟  
2. **هل الظهور على الويب أولاً كافٍ للإطلاق** ثم iOS/Android، أم نلتزم بالتسلسل الرسمي Backend → iOS → Android → Web؟  
3. **نوافذ التذكير الافتراضية:** هل توافقون على `7 / 1 / 0` أيام؟ أم تريدون أيضاً «قبل شهر» للأحداث البعيدة (مثل كسوف 2027)؟  
4. **اسم المنتج في الواجهة:** «ذكّرني» أم «متابعة الحدث» أم «أضف تنبيه»؟

بعد إجابتك على هذه النقاط نفتح Umbrella Issue ونبدأ PR الـ Schema/Backend دون توسيع لأنظمة مجاورة.
