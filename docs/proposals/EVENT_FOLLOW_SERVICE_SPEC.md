# مواصفة خدمة: متابعة أحداث الأخبار (Event Follow Service)

> **الحالة:** مواصفة منتج/تقنية — بانتظار الموافقة قبل التنفيذ  
> **الإصدار:** 1.0  
> **التاريخ:** 2026-07-31  
> **المالك المقترح:** editorial + platform (إشعارات)  
> **الأنظمة المرتبطة:** `calendar` · `push-notifications` · التحرير (ربط المقال)  
> **مرجع مختصر:** [`ARTICLE_EVENT_REMINDERS.md`](./ARTICLE_EVENT_REMINDERS.md)

---

## 1. ملخص تنفيذي

خدمة تمكّن سبق من التعامل مع الأخبار ذات **حدث قادم بتاريخ معروف** عبر مسارين على **نفس الحدث**:

| المسار | الجمهور | ماذا يفعل؟ |
|--------|---------|------------|
| **أ — تذكير تحريري** | محررو غرفة الأخبار | تذكير **قبل** الحدث (أسبوع / يوم) لتجهيز ونشر التغطية |
| **ب — متابعة العضو** | الزائر المسجّل عضوية | يضغط «متابعة الحدث» على المقال → يُشعر **يوم حلول الحدث** و/أو عند **نشر تغطية جديدة** |

**قاعدة ذهبية:** تذكيرات «قبل أسبوع / قبل يوم» للمحررين فقط. العضو لا يُزعج قبل الموعد.

---

## 2. المشكلة والقيمة

### 2.1 المشكلة
- أخبار كثيرة تتحدث عن حدث لاحق (كسوف، قانون، مناسبة، فعالية).
- المقال يُنشر ويُنسى؛ الغرفة قد تفوّت نافذة التغطية.
- العضو المهتم لا يملك طريقة رسمية ليقول: «ذكّروني لما يجي الوقت / لما تنشروا عنه».

### 2.2 القيمة
- **للتحرير:** تخطيط أوضح + تذكيرات تشغيلية قبل الموعد.
- **للعضو:** علاقة مستمرة مع الخبر تتجاوز لحظة القراءة.
- **للمنتج:** رفع العودة للتطبيق/الموقع حول أحداث حقيقية.

### 2.3 أمثلة استخدام

| الخبر | تاريخ الحدث | سلوك المحرر | سلوك العضو |
|-------|-------------|-------------|------------|
| كسوف كلي تشهده مصر والسعودية | 2 أغسطس 2027 | حدث تقويم + تذكير 7 أيام و1 يوم | متابعة → إشعار يوم 2 أغسطس + عند نشر تغطية |
| قانون يدخل حيّز التنفيذ بعد 45 يوماً | تاريخ محسوب | نفس المسار | نفس المسار |
| مناسبة وطنية / يوم عالمي مرتبط بمقال | تاريخ المناسبة | ربط بتقويم / أيام عالمية | متابعة من المقال |

**خارج النطاق:** مباريات VARA/الرياضة تبقى على `sports_follows` — لا تُنقل لهذه الخدمة.

## 3. المبادئ والحدود

### 3.1 داخل النطاق
- حدث واحد كمصدر حقيقة في `calendar_events`.
- تذكيرات تحريرية عبر `calendar_reminders`.
- ربط مقالات ↔ حدث.
- اشتراك عضو per-user على الحدث.
- إشعارات In-App + Push للعضو (يوم الحدث / تغطية جديدة).
- واجهة شريط على صفحة المقال + أدوات ربط في لوحة التحرير.

### 3.2 خارج النطاق (MVP)
- استخراج AI تلقائي ينشر للقارئ بلا موافقة محرر.
- تذكيرات مبكرة للعضو (7/1 أيام).
- تذكير محلي على الجهاز (AlarmManager / UNNotification) كمصدر حقيقة.
- الولاء / نقاط على المتابعة.
- iFox جدولة النشر كبديل للحدث.
- تطوير داخل `android/` (Capacitor القديم).

### 3.3 قرارات منتج مثبتة في هذه المواصفة

| القرار | القيمة الافتراضية في المواصفة |
|--------|-------------------------------|
| نص الزر للعضو | **متابعة الحدث** |
| تذكير المحرر الافتراضي | قبل **7** أيام وقبل **1** يوم |
| تنبيه يوم الحدث للعضو | صباح يوم الحدث، **08:00 Asia/Riyadh** |
| عدة تغطيات في نفس اليوم | **إشعار لكل مقال منشور** مربوط بالحدث (مع dedupe per user+article) |
| مصدر الحدث | `calendar_events` (لا جدول أحداث موازٍ للقارئ) |

## 4. المعمارية العامة

```
                         ┌──────────────────────────┐
                         │     calendar_events      │
                         │  (مصدر حقيقة الحدث)      │
                         └────────────┬─────────────┘
                                      │
                 ┌────────────────────┼────────────────────┐
                 │                    │                    │
                 ▼                    ▼                    ▼
      calendar_reminders     article ↔ event link   user_event_follows
      (محررون فقط)           (مقالات التغطية)        (أعضاء فقط)
                 │                    │                    │
                 ▼                    ▼                    ▼
      Job تذكير تحريري      خطاف publishArticle   Job يوم الحدث
      IN_APP تحريري         → إشعار تغطية جديدة   → إشعار العضو
```

## 5. نموذج البيانات

### 5.1 الموجود ويُعاد استخدامه

#### `calendar_events`
| حقل | ملاحظات |
|-----|---------|
| `id`, `title`, `slug` | هوية الحدث |
| `dateStart`, `dateEnd` | موعد الحدث (timestamptz) |
| `timezone` | افتراضي `Asia/Riyadh` |
| `type` | GLOBAL / NATIONAL / INTERNAL |
| `importance` | 1–5 |
| `description`, `tags`, `categoryId` | سياق تحريري |
| `createdById`, timestamps | تدقيق |

#### `calendar_reminders`
| حقل | ملاحظات |
|-----|---------|
| `eventId` | FK للحدث |
| `fireWhen` | عدد الأيام **قبل** الحدث (مثال: 7، 1) |
| `channel` | IN_APP / EMAIL / WHATSAPP / SLACK — للتحرير |
| `enabled` | تفعيل/تعطيل |

### 5.2 جديد مطلوب

#### أ) ربط المقال بالحدث

**الخيار الموصى به (مرن لعدة تغطيات):** جدول ربط

```
article_event_links
──────────────────
id                  PK
articleId           FK → articles.id  (unique إن أردنا مقال→حدث واحد في MVP)
calendarEventId     FK → calendar_events.id
role                text  — 'origin' | 'coverage'  (المقال الأول / تغطية لاحقة)
createdById         FK → users.id (nullable)
createdAt           timestamp
```

فهارس مقترحة:
- `(calendarEventId, createdAt)`
- `UNIQUE(articleId)` في الـ MVP (مقال واحد ↔ حدث واحد)

**بديل أبسط:** عمود `articles.calendarEventId` فقط — يكفي للـ MVP إن لم نحتج `role`.

#### ب) اشتراك العضو

```
user_event_follows
─────────────────
id                      PK
userId                  FK → users.id
calendarEventId         FK → calendar_events.id
channels                text[]  — افتراضي ['inapp','push']
notifyOnEventDay        boolean — افتراضي true
notifyOnNewCoverage     boolean — افتراضي true
sourceArticleId         FK → articles.id (المقال الذي ضغط منه المتابعة)
eventDayNotifiedAt      timestamptz nullable
isActive                boolean — افتراضي true
createdAt / updatedAt
```

قيود:
- `UNIQUE(userId, calendarEventId)`
- فهرس `(calendarEventId)` للإرسال الجماعي
- فهرس `(userId, isActive)` لقائمة «متابعاتي»

#### ج) سجل إرسال تغطية (dedupe) — موصى به

```
user_event_coverage_deliveries
─────────────────────────────
id
userId
calendarEventId
articleId
inboxNotificationId   nullable
sentAt
```

- `UNIQUE(userId, articleId)` حتى لا يُعاد إرسال نفس التغطية.

### 5.3 ما لا نضيفه
- لا `remindOffsets` على اشتراك العضو.
- لا جدول أحداث موازٍ للقارئ منفصل عن التقويم في الـ MVP.

## 6. العقود السلوكية

### 6.1 مسار أ — المحررون

1. محرر ينشئ حدثاً في التقويم أو من محرر المقال («إنشاء حدث من هذا الخبر» / «ربط بحدث»).
2. يُنشأ افتراضياً تذكيران: `fireWhen=7` و`fireWhen=1` بقناة `IN_APP` (قابلة للتعديل).
3. Job hourly/daily:
   - لكل تذكير مفعّل: إذا `dateStart - now` (بأيام تقويم Asia/Riyadh) == `fireWhen` ولم يُرسل بعد → أرسل لمستلمي التحرير.
4. مستلمو التحرير (MVP): المستخدمون ذوو صلاحية تقويم/تحرير مناسبة (نفس جمهور تقويم سبق الحالي / assignments إن وُجدت). **لا يُرسل للأعضاء.**
5. نص نموذجي:
   - «تذكير تحريري: «{title}» بعد أسبوع — جهّزوا التغطية»
   - «تذكير تحريري: «{title}» غداً — موعد النشر قريب»

**Gotcha تشغيلي حالي:** job التقويم موجود في `server/jobs/calendar.ts` لكن يحتاج تأكيداً أنه مُشغَّل من `server/index.ts` وأن مسار الإرسال ليس stub معطّلاً.

### 6.2 مسار ب — العضو

#### الظهور على المقال
يظهر شريط الحدث إذا:
- المقال له `article_event_links` نشط إلى حدث، **و**
- `calendar_events.dateStart` ≥ بداية اليوم الحالي (بتوقيت الحدث)، **و**
- الحدث غير ملغى/مخفي للعموم (إن أضفنا لاحقاً علم `memberVisible`؛ في MVP: كل حدث مربوط بمقال منشور يُعرض).

محتوى الشريط:
- عنوان الحدث
- التاريخ بصيغة عربية
- عدّ تنازلي بسيط (اختياري في MVP)
- زر **متابعة الحدث** / **متابَع**

#### المتابعة
- تتطلب عضوية مسجّلة الدخول.
- غير المسجّل → توجيه لتسجيل الدخول ثم العودة للمقال.
- POST ينشئ/يعيد تفعيل `user_event_follows`.
- DELETE يلغي (`isActive=false` أو حذف صلب — يُفضَّل soft في MVP).

#### إشعار يوم الحدث
- Job يومي ≈ 08:00 Asia/Riyadh (أو كل ساعة مع نافذة صباحية).
- شرط: `dateStart` يقع في «اليوم» بتوقيت الحدث، و`notifyOnEventDay=true`، و`eventDayNotifiedAt IS NULL`، و`isActive`.
- بعد الإرسال: تعبئة `eventDayNotifiedAt`.
- نص: «الحدث الذي تتابعه: «{title}» يحل اليوم»
- Deep link: أحدث مقال تغطية منشور مرتبط بالحدث، وإلا `sourceArticleId`.

#### إشعار تغطية جديدة
- عند انتقال مقال إلى حالة منشور وهو مربوط بـ `calendarEventId`:
  - لكل follow نشط بـ `notifyOnNewCoverage=true`
  - باستثناء ناشر المقال إن كان عضواً عادياً؟ (تجاهل في MVP)
  - مع dedupe عبر `user_event_coverage_deliveries`
- نص: «تحديث عن حدث تتابعه: «{article.title}»»
- Deep link: المقال الجديد.

#### بعد مرور الحدث
- بعد انتهاء يوم `dateStart` (أو `dateEnd` إن وُجد): الشريط يختفي من المقالات.
- المتابعات تبقى في السجل؛ لا إرسال إضافي ليوم الحدث.
- تغطية لاحقة بعد الحدث: ما زال يمكن إشعار `notifyOnNewCoverage` لمدة سماح (مقترح MVP: **7 أيام بعد dateStart** ثم يتوقف تلقائياً أو تُعطّل المتابعة).

## 7. واجهات برمجية (API)

### 7.1 عامة / قراءة

| Method | Path | Auth | الوصف |
|--------|------|------|-------|
| GET | `/api/articles/:idOrSlug` (توسيع الاستجابة) | عام | يضم كائن `anchoredEvent` إن وُجد |
| GET | `/api/v1/articles/:id` (توسيع) | Bearer اختياري | نفس الحقل + `isFollowing` إن وُجدت جلسة |

شكل `anchoredEvent` المقترح:

```json
{
  "id": "evt_…",
  "title": "كسوف كلي — أغسطس 2027",
  "dateStart": "2027-08-02T00:00:00.000+03:00",
  "timezone": "Asia/Riyadh",
  "daysRemaining": 367,
  "isFollowing": false
}
```

### 7.2 عضوية — متابعة

| Method | Path | Auth | Body | نتيجة |
|--------|------|------|------|-------|
| POST | `/api/calendar/events/:eventId/follow` | Passport session | `{ "channels"?: ["inapp","push"], "sourceArticleId"?: "…" }` | 200 follow |
| DELETE | `/api/calendar/events/:eventId/follow` | Passport session | — | 200 unfollowed |
| GET | `/api/calendar/events/my-follows` | Passport session | — | قائمة متابعات العضو |
| POST | `/api/v1/calendar/events/:eventId/follow` | Bearer | نفس الـ body | موبايل |
| DELETE | `/api/v1/calendar/events/:eventId/follow` | Bearer | — | موبايل |
| GET | `/api/v1/calendar/events/my-follows` | Bearer | — | موبايل |

أخطاء متوقعة:
- `401` غير مسجّل
- `404` حدث غير موجود
- `409` متابعة مكررة نشطة (أو 200 idempotent — **يُفضَّل idempotent 200**)

### 7.3 تحرير — ربط مقال

| Method | Path | Auth / صلاحية | الوصف |
|--------|------|---------------|-------|
| POST | `/api/calendar/events` | تقويم/تحرير | إنشاء حدث (موجود) |
| POST | `/api/calendar/events/:eventId/reminders` | تقويم | ضبط تذكيرات 7/1 (موجود جزئياً) |
| PUT | `/api/articles/:id/event-link` | تحرير مقال | `{ "calendarEventId": "…" \| null, "role"?: "origin"\|"coverage" }` |
| POST | `/api/articles/:id/create-event-from-article` | تحرير | ينشئ حدثاً من عنوان/تاريخ مدخل ويربطه |

حقول النموذج في محرر المقال:
- هل الخبر عن حدث قادم؟ (نعم/لا)
- عنوان الحدث
- تاريخ (ووقت اختياري)
- أو اختيار حدث تقويم موجود

## 8. الإشعارات

### 8.1 أنواع `notifications_inbox.type` المقترحة

| type | الجمهور |
|------|---------|
| `calendar.editorial_reminder` | محررون |
| `calendar.member_event_day` | أعضاء |
| `calendar.member_coverage` | أعضاء |

### 8.2 القنوات

| قناة | محرر | عضو |
|------|------|-----|
| In-App (`notifications_inbox` + bus) | ✅ | ✅ |
| Push (FCM/APNs عبر `push_devices`) | اختياري لاحقاً | ✅ إن اختار `push` |
| EMAIL / SLACK | تحريري لاحقاً | ❌ MVP |

### 8.3 قوالب النصوص (عربية)

| الحالة | العنوان | النص |
|--------|---------|------|
| تحريري −7 | تذكير تحريري | «{title}» بعد أسبوع — جهّزوا التغطية |
| تحريري −1 | تذكير تحريري | «{title}» غداً — موعد التغطية قريب |
| عضو · يوم الحدث | حدث تتابعه | «{title}» يحل اليوم |
| عضو · تغطية | تحديث عن حدث تتابعه | {articleTitle} |

### 8.4 Deep links

| منصة | يوم الحدث | تغطية جديدة |
|------|-----------|-------------|
| ويب | `/article/{slug}` | `/article/{newSlug}` |
| تطبيق سبق | `sabq://article/{id}` | نفس النمط |
| لوحة تحرير (تذكير) | `/dashboard/calendar` أو صفحة الحدث | — |

### 8.5 إعادة الاستخدام التقني
- نمط الإرسال المزدوج كما في التنبيهات الرياضية (`sportsAlertsService` + `notificationBus`).
- Leader election على كل Job.
- لا تعتمد على `notificationEngine.createNotification` إن بقي معطّلاً — استخدم المسار الحي للإشعارات.

## 9. Jobs والجدولة

| Job | الجدول المقترح | المسؤولية |
|-----|----------------|-----------|
| `processEditorialCalendarReminders` | كل ساعة | تذكيرات `calendar_reminders` للمحررين |
| `memberEventDayJob` | يومياً 08:00 Asia/Riyadh (أو كل ساعة مع فلتر النافذة) | إشعار يوم الحدث للأعضاء |
| خطاف مزامنة (ليس cron) | عند `article.status → published` | إشعار تغطية للمتابعين |

متطلبات مشتركة:
- قفل عدم التداخل (`isProcessing` / leader election).
- سجلات واضحة: عدد المرشحين / المُرسل / الفاشل.
- Idempotency عبر حقول `eventDayNotifiedAt` وجدول deliveries.

## 10. واجهات المستخدم

### 10.1 شريط العضو على المقال (ويب)

```
┌──────────────────────────────────────────────────────────┐
│  حدث قادم · 2 أغسطس 2027                                 │
│  كسوف كلي تشهده مصر والسعودية                             │
│  متبقّي: سنة ويومان                    [ متابعة الحدث ]  │
└──────────────────────────────────────────────────────────┘
```

حالات الزر:
- غير مسجّل → يفتح تدفق الدخول
- مسجّل وغير متابع → «متابعة الحدث»
- متابع → «متابَع» (ثانوي) مع إمكانية إلغاء

مبادئ UI: شريط واحد واضح ضمن نظام تصميم الويب الحالي؛ ليس بطاقة بطبقات؛ لا يغطي صورة البطل بعناصر عائمة منفصلة.

### 10.2 محرر المقال / التقويم
- حقول ربط الحدث (قسم جانبي أو أسفل الميتاداتا).
- عند الإنشاء: اقتراح تذكيرات 7 و1 مفعّلة.
- رابط سريع لفتح الحدث في `/dashboard/calendar`.

### 10.3 موبايل (iOS مرجع، Android يطابق 1:1)
- نفس المعلومات والـ CTA على شاشة المقال.
- استقبال Push بأنواع الخدمة الجديدة.
- قائمة «أحداث أتابعها» يمكن تأجيلها لما بعد MVP الشريط.

### 10.4 مركز المتابعات (لاحقاً)
- بجانب متابعة القصص في «متابعاتي»: الحدث · التاريخ · حالة المتابعة · رابط المقال.

## 12. القواعد الحدّية وحالات خاصة

| الحالة | السلوك |
|--------|--------|
| حدث بلا مقالات مربوطة | يظهر في التقويم التحريري فقط؛ لا شريط عضو |
| مقال عن حدث مضى | لا شريط |
| إلغاء الحدث من التحرير | إخفاء الشريط؛ إيقاف jobs؛ (اختياري) إشعار واحد «أُلغي الحدث الذي تتابعه» — خارج MVP |
| تعديل `dateStart` | تذكيرات المحرر تُحسب من التاريخ الجديد؛ إن تغيّر يوم الحدث بعد إرسال إشعار العضو لا يُعاد الإرسال إلا إذا صُفّر `eventDayNotifiedAt` يدوياً/بسياسة واضحة |
| عضو تابع ثم حذف حسابه | CASCADE على المتابعات |
| مقال إنجليزي/أردو | MVP عربي أولاً؛ نفس الربط لاحقاً عبر جداول en/ur إن لزم |
| أهمية الحدث INTERNAL بحتة | يُفضَّل عدم ربطه بمقال عام / أو علم `memberVisible=false` لاحقاً |

## 13. الخصوصية والأمان
- لا تُعرض قائمة متابعي الحدث للعامة.
- إشعارات العضو شخصية لـ `userId` فقط.
- لا تُرسل بيانات أعضاء خارج البنية الحالية للإشعارات.
- احترام تفضيلات الإشعار العامة للعضوية إن وُجدت (إن قناة push مغلقة عالمياً → In-App فقط).

## 16. اختبارات قبول (Acceptance)

1. محرر ينشئ حدثاً بتاريخ بعد 10 أيام مع تذكيرات 7 و1 → عند حلول نافذة −7 يصل إشعار تحريري فقط (لا أعضاء).
2. مقال منشور مربوط بالحدث → العضو يرى الشريط وزر المتابعة.
3. زائر بلا دخول يضغط المتابعة → يُطلب منه الدخول.
4. عضو يتابع → يظهر في `my-follows` وحالة الزر «متابَع».
5. نشر مقال تغطية ثانٍ مربوط بنفس الحدث → المتابع يستلم إشعار تغطية مرة واحدة فقط لنفس المقال.
6. صباح يوم الحدث → المتابع يستلم إشعار يوم الحدث مرة واحدة فقط.
7. بعد يوم الحدث → الشريط لا يظهر؛ لا يتكرر إشعار يوم الحدث.
8. إلغاء المتابعة → لا إشعارات لاحقة.
9. مباراة رياضية لا تستخدم هذا المسار.
