# البوابة الرياضية — خارطة الطريق (الموجات المتبقّية)

> **الحالة:** تخطيط — لم تُنفَّذ بعد.
> **مرجع:** [`SPORTS_HUB.md`](SPORTS_HUB.md) · [`SPORTS_HUB_WAVE1.md`](SPORTS_HUB_WAVE1.md) (المنفّذة).
> **آخر تحديث:** 2026-06-17

هذه الوثيقة تُفصّل كل بند إثراء متبقٍّ بالمستوى المطلوب للتنفيذ المباشر: **الـ endpoint الدقيق، شكل البيانات الخام من المزوّد، نقطة الدمج في الكود، استراتيجية الكاش (TTL)، الـ gotchas**. كل بند مكتفٍ ذاتياً ويمكن تنفيذه كـ PR منفصل على نمط الموجة 1.

> **المزوّد:** API-Football (`https://v3.football.api-sports.io`) · المفتاح `APIFOOTBALL_KEY` (خطة Mega مغطّاة). كل النداءات عبر `apiGet(path, params)` الخلف `withSWR(key, ttl, staleTtl, fn)`.

---

## قواعد عامة لكل بند (مكرّرة من الموجة 1)

1. **لا `db`** — كل الوصول عبر `saudiLeagueService.ts` (ADR-001).
2. **خلف `withSWR` دائماً** مع مفتاح مميَّز (`spl:<feature>:<id>`) وTTL مناسب.
3. **DTO عربي** عبر خرائط في [`saudiLeagueNames.ts`](../server/services/saudiLeagueNames.ts) (أضف المفاتيح الناقصة).
4. **graceful degradation** — ترجع `null`/`[]` عند الفشل، وتُخفي الواجهة البطاقة.
5. **تحقّق من المعاملات المدعومة** لكل endpoint — راجع [درس timezone](SPORTS_HUB_WAVE1.md#المشكلة-2--502-بسبب-timezone-غير-المدعوم): معاملات API-Football غير موحّدة بين النقاط.
6. **`player id` و`team id` عامّان** عند المزوّد — لا يحتاجان تحديد بطولة.

## 🌊 الموجة 2 — قيمة عالية، تكلفة متوسطة

### البند 5 — رسم بياني لتطوّر أداء اللاعب عبر المواسم

**الهدف:** في `SportsPlayer.tsx`، خطّ زمني (Sparkline/Line) يُظهر الأهداف والمشاركات عبر آخر 3-4 مواسم — يكشف «الموسم الانفجاري» أو التراجع.

| | |
|---|---|
| **الـ Endpoint** | `players?id={playerId}&season={Y}` (نداءة واحدة لكل موسم) |
| **شكل البيانات الخام** | `response[0].statistics[]` — كل عنصر فيه `games.appearences`، `goals.total`، `goals.assists`، `league.name` |
| **نقطة الدمج Backend** | دالة `getPlayerSeasonHistory(playerId, seasons[])` → ترجع `SplPlayerSeasonPoint[]` لكل موسم |
| **TTL المقترح** | طويل (`CACHE_TTL.LONG`) — بيانات تاريخية لا تتغيّر |
| **تحسين الكلفة** | اجلب موسم روشن الحالي أولاً (`seasonFor(proLeague)`) ثم ارجع للخلف: `season, season-1, season-2, season-3`. كل نداءة خلف `withSWR` بـ key موسمي مستقل، فيُعاد استخدامها إن طُلبت لاحقاً |
| **تحسين الكلفة (2)** | `Promise.all` على المواسم الأربعة بالتوازي |
| **تحذير** | اللاعب قد لا يكون في الدوري السعودي كل موسم — اعرض مواسمه في أي دوري، مع ترجمة اسم الدوري |
| **نقطة الواجهة** | بطاقة جديدة «تطوّر الأداء» فوق «أرقام الموسم» في `SportsPlayer.tsx`. استعمل مكوّن رسم خفيف (SVG inline أو `recharts` إن كان موجوداً — تحقّق قبل إضافة dependency) |
| **PR مرجعي للنمط** | `getPlayerCard` في الموجة 1 (#329) |

### البند 6 — سجلّ انتقالات اللاعب

**الهدف:** في `SportsPlayer.tsx`، قائمة انتقالات اللاعب: متى، من أي نادٍ إلى أي نادٍ، وقيمة الصفقة (إن وُجدت).

| | |
|---|---|
| **الـ Endpoint** | `transfers?player={playerId}` |
| **شكل البيانات الخام** | `response[].transfers[]` — كل انتقال فيه `date`, `type` (free/loan/n/a), `teams.in.{id,name,logo}`, `teams.out.{id,name,logo}` |
| **نقطة الدمج Backend** | دالة `getPlayerTransfers(playerId)` → `SplPlayerTransfer[]` مرتّبة تنازلياً بالتاريخ |
| **TTL المقترح** | طويل — الانتقالات تاريخية لا تتغيّر |
| **تحذير** | بعض اللاعبين قد لا يكون لهم انتقالات (وُلدوا في النادي). عالج الحالة الفارغة |
| **ربط داخلي** | `teams.in.id` و`teams.out.id` → ربط لـ `/sports2/team/:id` (إن كان النادي في خرائطنا) |
| **ترجمة** | أسماء الأندية عبر `localizeSplTeamName(id, name)`. نوع الانتقال عبر خريطة عربية جديدة: `free→انتقال حر`, `loan→إعارة`, `n/a→غير معلوم` |
| **نقطة الواجهة** | بطاقة «مسيرة الانتقالات» في `SportsPlayer.tsx` (شبيهة ببطاقة «المسيرة» الحالية لكن بالتفصيل) |

### البند 7 — سجلّ إصابات اللاعب

**الهدف:** في `SportsPlayer.tsx`، آخر الإصابات: النوع، تاريخ البداية، والمدة المتوقّعة.

| | |
|---|---|
| **الـ Endpoint** | `injuries?player={playerId}` |
| **شكل البيانات الخام** | `response[]` — كل عنصر فيه `player.*`, `team.*`, `league.*`, `fixture.*`, `type` (Missing/Injured), `reason` (نص مثل "Knee Injury"), `date` |
| **نقطة الدمج Backend** | دالة `getPlayerInjuries(playerId, limit=8)` → `SplPlayerInjury[]` مرتّبة تنازلياً |
| **TTL المقترح** | متوسط-طويل (1 ساعة) — الإصابات تتحدّث |
| **تحذير** | ركّز على آخر 5-8 إصابات فقط (قد يطول السجلّ للاعبين القدامى). أعرض السبب بالإنجليزية إن لم يُترجم |
| **نقطة الواجهة** | بطاقة طيّية «الإصابات» في `SportsPlayer.tsx` — إصابات حديثة بارزة + قائمة قابلة للطيّ |

### البند 8 — آخر انتقالات النادي (وصل/غادر)

**الهدف:** في `SportsTeam.tsx`، تبويب يُظهر آخر اللاعبين الذين وصلوا النادي وغادروه (نافذة انتقالات).

| | |
|---|---|
| **الـ Endpoint** | `transfers?team={teamId}` |
| **شكل البيانات الخام** | نفس البند 6 لكن مفلتر على النادي. اميّز الوصول (`teams.in.id === teamId`) من المغادرة (`teams.out.id === teamId`) |
| **نقطة الدماج Backend** | دالة `getTeamTransfers(teamId, limit=20)` → `{ arrivals: SplTransfer[], departures: SplTransfer[] }` مفلتر على آخر نافذة |
| **TTL المقترح** | متوسط (1 ساعة) — يتغيّر في النوافذ |
| **تحذير** | قد يكون السجلّ ضخماً (تاريخ كامل) — اقطع آخر 30 يومًا أو آخر 20 انتقال |
| **نقطة الواجهة** | بطاقة بتبويبين «وصل»/«غادر» في `SportsTeam.tsx` |
| **نقطة API** | `GET /api/sports/team/:id/transfers` |

### البند 9 — ترويسة البطولة الديناميكية

**الهدف:** عند تبديل البطولة في `SportsHub.tsx`، تظهر ترويسة فيها شعار البطولة + موسمها الحالي + جولتها الجارية.

| | |
|---|---|
| **الـ Endpoint** | `leagues?id={compId}` (نداءة واحدة) |
| **شكل البيانات الخام** | `response[0].league.{name, logo}` + `response[0].seasons[]` (كل عنصر فيه `year`, `start`, `end`, `current`) |
| **نقطة الدماج Backend** | دالة `getCompetitionMeta(comp)` → `{ name, logo, season, currentRound? }`. لاحظ أن `currentRound` قد يحتاج نداءة `fixtures/rounds?league&season&current=true` إضافية |
| **TTL المقترح** | `SEASON_TTL` (6 ساعات) — شبه ثابت |
| **تحذير** | `seasonFor` القائم يستدعي نفس الـ endpoint لكن يأخذ الموسم فقط. وسّعها لتُرجع `logo` أيضاً بدل نداءة جديدة، أو استخدم نداءة `leagues?id` مكاشفة |
| **نقطة الواجهة** | ترويسة بصرية أعلى مبدّل البطولات تُظهر الشعار والموسم |
| **نقطة API** | يمكن إثراء `GET /api/sports/competitions` القائم بإضافة `logo` و`season` لكل بطولة (بدل نقطة جديدة) |

## 🌊 الموجة 3 — لمسات نهائية متميّزة

### البند 10 — Pitch View للتشكيلة (أرض ملعب)

**الهدف:** في `MatchDialog`، عرض التشكيلة موزّعة على أرض ملعب حسب التشكيلة (4-3-3...) بدل القائمة النصية الحالية.

| | |
|---|---|
| **لا يحتاج backend جديد** | البيانات موجودة في `lineups` (موجودة في `SplMatchDetail` عبر `getMatchDetail`) |
| **التحدّي** | `SplLineupPlayer` الحالي يحوي `pos` (G/D/M/F) لكن **لا يحوي إحداثيات**. API-Football يُرجع `startXI[].player.grid` (مثل `"4:4:2"` أو إحداثيات `x,y`) |
| **نقطة الدماج Backend** | وسّع `localizeLineupPlayer` لتأخذ `grid` من `p.player.grid` وتضيفه للـ DTO |
| **نقطة الواجهة** | مكوّن `PitchView` يرسم ملعباً (SVG أو div) ويضع اللاعبين حسب `grid`. ابسط احتياط: لو غاب `grid`، ارجع للقائمة النصية الحالية |
| **احتياط UX** | قد لا تتوفّر `grid` للمباريات القديمة — graceful fallback إجباري |

### البند 11 — تقييمات لاعبي المباراة + رجل المباراة الحقيقي

**الهدف:** تبويب «تقييمات اللاعبين» في `MatchDialog`، يرتّب لاعبي المباراة بحسب التقييم، ويبرز رجل المباراة الحقيقي (بدل التخمين الحالي من xG).

| | |
|---|---|
| **الـ Endpoint** | `fixtures/players?fixture={fixtureId}` |
| **شكل البيانات الخام** | `response[]` — كل عنصر فيه `team.*` + `players[].player.{id,name,photo,rating}` + `players[].statistics[]` (تسديدات/تمريرات/مراوغات...) |
| **نقطة الدماج Backend** | دالة `getMatchPlayerRatings(fixtureId)` → مرتّبة تنازلياً. أضفها لـ `SplMatchDetail` أو كنداءة منفصلة |
| **TTL المقترح** | `MATCH_DETAIL_TTL` (20s مباشر، ثم ثابت) |
| **تحذير التكلفة** | هذه نداءة خامسة في `getMatchDetail` (بعد events/statistics/lineups). قد تكون ضخمة (بيانات 22+ لاعب). **اقتراح:** لا تجلبها ضمن `getMatchDetail` الأساسي — اجعلها نقطة منفصلة تُطلب عند فتح تبويب التقييمات فقط (lazy) |
| **ربط داخلي** | كل لاعب يربط لـ `/sports2/player/:id` |
| **نقطة API** | `GET /api/sports/match/:id/players` (lazy) |

### البند 12 — توقّعات للمباريات القادمة (Predictions)

**الهدف:** على `MatchCard` للمباريات غير المبدوءة، نسبة فوز كل فريق (تحت المعلومات).

| | |
|---|---|
| **الـ Endpoint** | `predictions?fixture={fixtureId}` |
| **شكل البيانات الخام** | `response[0].predictions.{winner.{id,name}`, `percent.{home,draw,away}`, `comparison.*`, `under_over}` |
| **نقطة الدماج Backend** | دالة `getFixturePrediction(fixtureId)` → `{ homePct, drawPct, awayPct, winnerId? }` |
| **TTL المقترح** | متوسط (10-30 دقيقة) — التوقعات تُحدَّث |
| **تحذير التكلفة** | لا تجلب توقعات لكل مباراة في قائمة `matches` (قد تكون 20+ مباراة → 20 نداءة). **اقتراح:** اعرضها فقط داخل `MatchDialog` للمباريات غير المبدوءة |
| **تحذير المنطق** | لا تتوفّر التوقعات للمباريات المباشرة أو المنتهية — عالج الحالة الفارغة |
| **نقطة الواجهة** | شريط نسب ثلاثي (مضيف/تعادل/ضيف) أعلى التبويبات في `MatchDialog` |

### البند 13 — مؤشّر صعود/هبوط الترتيب

**الهدف:** في `StandingsTable`، سهم ↑↓ بجانب كل صفّ يُظهر تغيّر المركز مقارنة بالجولة السابقة.

| | |
|---|---|
| **التحدّي** | `standings` الحالي يُرجع الوضع الحالي فقط. مقارنة الجولات تحتاج بيانات تاريخية |
| **خيار A (بسيط، موصى به)** | احفظ لقطة من الترتيب في كل تحديث للكاش (كـ snapshot في الذاكرة أو Redis)، وقارن معها. تكلفة 0 نداءات إضافية لكن يحتاج بنية تخزين |
| **خيار B (نداءة مباشرة)** | API-Football **لا يوفّر ترتيب تاريخي مباشر** لكل جولة بسهولة — هذا الخيار مكلف وغير عملي |
| **نقطة الواجهة** | عمود جديد «التغيّر» في `StandingsTable`، سهم أخضر ↑/أحمر ↓/رمادي — |
| **ملاحظة** | هذا البند **الأعلى تكلفة** في الموجة 3 بسبب غياب بيانات المصدر المباشرة. أجّله إن لم تكن بنية الـ snapshot مريحة |
