# توسّع اتصالات قاعدة البيانات (Neon) — دليل تشغيلي

> الهدف: منع **تشبّع اتصالات القاعدة** الذي يُسقط الموقع عند الذروة أو النشر
> المتتابع — وهو ما حدث فعلًا (حادثة 2026-07-11: دفعة خبر عاجل «الأوامر الملكية»
> أشبعت المسبح خلال ثوانٍ فرجعت كل الطلبات 5xx).

## المشكلة باختصار
- قاعدة واحدة على Neon، وكل نسخة تشغيل (pod) تفتح حتى `DB_POOL_MAX` اتصالًا.
- الاتصال **المباشر** بـNeon محدود بـ **~112**؛ فمع **3 pods × 50 = 150 > 112**
  يحدث تشبّع → طابور على `pool.connect()` → مهلة → 5xx.
- **الحل الجوهري:** استخدام **نقطة `-pooler` (PgBouncer)** من Neon، وحدّها ~**10,000**.

## القاعدة الحاكمة
```
pods × DB_POOL_MAX  ≤  حدّ اتصالات المزوّد
   (المباشر ≈ 112   |   -pooler ≈ 10,000)
```

## الخطوات

### 1) فعّل نقطة الـ-pooler في Neon  ← الأهم
Neon يعطي مضيفَين لنفس القاعدة:
| النوع | المضيف | الحدّ |
|---|---|---|
| مباشر | `ep-xxxx.<region>.aws.neon.tech` | ~112 |
| **pooled** | `ep-xxxx-**pooler**.<region>.aws.neon.tech` | ~10,000 |

- من لوحة **Neon → Connection Details → فعّل «Pooled connection»** وانسخ سلسلة الـ`-pooler`.
- على **Railway**، اضبط `NEON_DATABASE_URL` على سلسلة الـ`-pooler` (أبقِ `?sslmode=require`):
  ```
  NEON_DATABASE_URL=postgresql://user:pass@ep-xxxx-pooler.<region>.aws.neon.tech/db?sslmode=require
  ```
- بعدها يصبح `50 × عدد كبير من الـpods` آمنًا.

### 2) اضبط `DB_POOL_MAX` (سقف الاتصالات لكل pod)
- الكود الآن يقرأ `DB_POOL_MAX` (افتراضي 50، محدود [1,500]) — لا تعديل كود لاحقًا.
- على **-pooler:** 50 آمن حتى عند عدد pods عالٍ.
- على **مباشر:** اضبطه بحيث `pods × DB_POOL_MAX < 112` (مثال: 3 pods → `DB_POOL_MAX=30` → 90).

### 3) اسقُف عدد الـreplicas (إجراء لوحة Railway)
> **لماذا ليس في `railway.json`؟** ملف `railway.json` هشّ — أي حقل غير معروف يرفضه
> محلّل Railway ويُفشل كل النشر (راجع Gotchas في CLAUDE.md)، وتثبيت `numReplicas`
> يُلغي التوسّع التلقائي وهو قرار سعة/تكلفة يخصّك. لذا يُضبط من اللوحة لا الملف.

- **Railway → الخدمة → Settings → Replicas / Autoscaling:** اضبط **الحدّ الأقصى**
  بحيث `max_replicas × DB_POOL_MAX ≤ حدّ المزوّد`.
  - مع الـ-pooler: الحدّ الأعلى للـreplicas يحكمه CPU/الإنتاجية لا الاتصالات.
  - بدون pooler: مثال — حدّ 112 و`DB_POOL_MAX=50` → **replicas ≤ 2**.

### 4) قِس نقطة الانهيار (k6)
```bash
# ثبّت k6: https://k6.io/docs/get-started/installation
BASE_URL=https://<staging-or-preview> ARTICLE_SLUG=<slug> k6 run load-test/breaking-point.js
# أو محليًا:
BASE_URL=http://localhost:3000 k6 run load-test/breaking-point.js
```
- السكربت يصعّد المستخدمين حتى ترتفع الأخطاء/الكمون — تلك نقطة الانهيار.
- **قبل** الـ-pooler: 5xx يظهر عند عدد VUs منخفض (تشبّع المسبح). **بعده:** يصمد أعلى بكثير.
- ⚠️ **لا تشغّله على الإنتاج دون نافذة صيانة** — إنه ضغط متعمّد.

## التحقق
- بعد الخطوات 1–2: راقب لوحة Neon — عدد الاتصالات النشطة يبقى منخفضًا ومستقرًّا (الـpooler يُوزّعها).
- أعد اختبار k6: يجب أن ترتفع نقطة الانهيار بشكل واضح مقارنةً بالمباشر.
- لا مزيد من 5xx / «JSON Parse: Unrecognized token '<'» عند دفعات الأخبار العاجلة.

## المتبقّي (تحسينات لاحقة)
- **نسخ قراءة (read replicas)** لتفريغ حمل القراءة عن الأساسي.
- **كاش محتوى Redis مشترك عبر الـpods** لتقليل ضربات القاعدة أصلًا.
