# تقرير فحص تهديد زرع روابط خارجية في المقالات

تاريخ الفحص: 15 مايو 2026  
نطاق الفحص: كود المشروع المحلي في `/Users/alialhazmi/sabq`، مع فحص مسارات إنشاء/تعديل/عرض المقالات، حماية الجلسات وCSRF، التعقيم، الصلاحيات، والأسرار والحزم.

## الخلاصة التنفيذية

لا يظهر من الكود أن شخصًا مجهولًا يستطيع تعديل المقالات مباشرة بدون حساب وصلاحيات. مسارات الإدارة العربية الأساسية محمية بالمصادقة والصلاحيات، وحماية CSRF مفعلة عمومًا للعمليات التي تغيّر البيانات.

لكن الخطر الحقيقي موجود في سياسة المحتوى نفسها: المشروع يسمح بتخزين وعرض HTML غني داخل المقالات، والتعقيم الحالي عند الحفظ يزيل بقايا تنسيقية فقط ولا يطبق سياسة أمان مركزية على الروابط. هذا يعني أن زرع روابط خارجية ممكن إذا حصل المهاجم على حساب محرر/ناشر، أو استغل قناة إدخال موثوقة مثل ناشر خارجي، استيراد محتوى، أو توليد آلي.

التقييم العام: متوسط إلى عال بالنسبة لتهديد روابط SEO spam، وأقل من ذلك بالنسبة لاختراق مباشر بدون اعتماديات مسروقة.

## النتائج الحرجة والعالية

### 1. تعقيم المقالات عند الحفظ ليس تعقيمًا أمنيًا كاملًا

الموقع: `server/utils/sanitizeArticleHtml.ts`

الدالة الحالية تنظف وسوم `span` وبعض أنماط الألوان فقط. لا تمنع الروابط الخارجية، ولا تضيف `rel="nofollow noopener noreferrer"`, ولا تحصر `iframe` أو `img` في نطاقات موثوقة، ولا تزيل كل خصائص HTML الخطرة.

الأثر:
- يمكن حفظ رابط خارجي داخل المقال إذا كان المستخدم لديه صلاحية إنشاء/تعديل.
- قد يؤدي ذلك إلى SEO spam أو تحويل المستخدمين لمواقع خبيثة.
- الاعتماد على DOMPurify في الواجهة جيد ضد XSS، لكنه لا يحل مشكلة تخزين روابط غير مرغوبة في قاعدة البيانات.

الحل:
- استبدال/توسيع `sanitizeArticleHtml` بتعقيم خادم حقيقي باستخدام `isomorphic-dompurify`.
- تطبيق allowlist للوسوم والخصائص.
- السماح بروابط داخلية فقط افتراضيًا، أو السماح بقائمة نطاقات موثوقة.
- إضافة `rel="nofollow noopener noreferrer"` و`target="_blank"` للروابط الخارجية المصرح بها.
- تسجيل أي رابط خارجي جديد في سجل تدقيق.

### 2. مسارات English articles لا تطبق نفس تعقيم المقالات العربية

المواقع:
- `server/routes.ts` عند `POST /api/en/dashboard/articles`
- `server/routes.ts` عند `PATCH /api/en/dashboard/articles/:id`
- المخطط: `shared/schema.ts` عند `insertEnArticleSchema`

المسارات الإنجليزية تمرر `content` مباشرة بعد تحقق Zod بسيط، دون استدعاء `sanitizeArticleHtml`.

الأثر:
- اختلاف سياسة الأمان بين العربي والإنجليزي.
- أي محرر إنجليزي يمكنه تخزين HTML وروابط بدون تنظيف خادم.

الحل:
- تطبيق نفس sanitizer المركزي على `requestData.content` و`updateData.content`.
- توحيد مخططات المقالات بحيث لا يكون `content` مجرد string مفتوح.

### 3. مسارات الناشرين تسمح بحفظ مسودات تحتوي روابط دون تنظيف خادم

المواقع:
- `server/routes.ts` عند `POST /api/publisher/articles`
- `server/routes.ts` عند `PATCH /api/publisher/articles/:id`
- `server/storage.ts` عند `updatePublisherArticle`

يوجد تحقق جيد من الملكية وحالة المسودة، لكنه لا ينظف HTML قبل الحفظ.

الأثر:
- لو كان حساب ناشر مخترقًا أو غير موثوق، يمكن إدخال روابط في المسودة.
- إذا وافق مشرف على المقال بدون مراجعة روابط، تنتقل الروابط إلى النشر.

الحل:
- تنظيف المحتوى عند حفظ مسودات الناشرين.
- إضافة خطوة مراجعة إلزامية تعرض “روابط خارجية مكتشفة” قبل الموافقة.
- منع نشر مقال ناشر يحتوي روابط خارجية غير مصرح بها.

### 4. سياسة عرض المقالات تسمح بالروابط الخارجية بعد التعقيم

المواقع:
- `client/src/pages/ArticleDetail.tsx`
- `client/src/pages/en/EnglishArticleDetail.tsx`
- `client/src/pages/ur/ArticleDetail.tsx`

DOMPurify مستخدم عند العرض، وهذا جيد ضد `javascript:` والسكريبتات. لكن الإعدادات تسمح بالروابط الخارجية العادية مثل `https://example.com`.

الأثر:
- هذا ليس XSS بحد ذاته، لكنه يحقق تهديد “زرع روابط خارجية”.

الحل:
- تطبيق سياسة روابط بعد DOMPurify: الروابط الخارجية إما تزال، أو تتحول إلى نص، أو تضاف لها وسم تحذير/`nofollow`.
- الأفضل تنفيذها في الخادم عند الحفظ، ثم إبقاء الواجهة كطبقة دفاع ثانية.

## نتائج متوسطة

### 5. CSP ما زالت واسعة نسبيًا

الموقع: `server/index.ts`

في الإنتاج `scriptSrc` يسمح بـ `unsafe-inline` و`https:` و`blob:`، و`frameSrc` يسمح بأي HTTPS.

الأثر:
- أي XSS مستقبلي سيكون أثره أكبر.
- السماح العام للـ iframe قد يعزز إدراج مصادر خارجية.

الحل:
- تقليل `frameSrc` إلى YouTube/Twitter/مصادر موثوقة محددة.
- إزالة `unsafe-inline` تدريجيًا باستخدام nonce أو hash.
- تضييق `scriptSrc` إلى النطاقات المطلوبة فقط.

### 6. استثناءات CSRF واسعة وتحتاج مراجعة دورية

الموقع: `server/csrf.ts`

حماية CSRF مفعلة، لكن توجد استثناءات كثيرة، وبعضها يستخدم `startsWith` مثل `/api/articles/` و`/api/shortlinks`.

الأثر:
- ليست ثغرة مؤكدة الآن، لكنها مخاطرة صيانة: أي مسار تعديل جديد تحت بادئة مستثناة قد يصبح بلا CSRF.

الحل:
- تحويل الاستثناءات إلى قائمة دقيقة بالمسار والطريقة، لا بادئات عامة.
- إضافة اختبار يمنع إضافة POST/PATCH/DELETE تحت بادئة مستثناة بدون مراجعة.

### 7. Webhook البريد قد يكون غير محمي إذا لم يضبط السر

الموقع: `server/routes/emailAgent.ts`

يوجد تحذير صريح أن `SENDGRID_INBOUND_SECRET` إذا لم يضبط فسيكون webhook غير موثق.

الأثر:
- إذا كان webhook يستقبل محتوى قابلًا للتحويل إلى مقالات أو مسودات، فهو قناة إدخال حساسة.

الحل:
- جعل السر إلزاميًا في الإنتاج.
- رفض الطلبات بدل التحذير فقط عند غياب السر.

## خطة المعالجة المقترحة

الأولوية خلال 24 ساعة:
1. جعل `sanitizeArticleHtml` تعقيمًا أمنيًا مركزيًا حقيقيًا.
2. تطبيقه على العربي والإنجليزي والأردو ومسارات الناشرين وكل استيراد أو توليد آلي.
3. إضافة كاشف روابط خارجية قبل النشر يعرض قائمة الروابط ويمنع غير المصرح.
4. جعل `SENDGRID_INBOUND_SECRET` إلزاميًا في الإنتاج.

الأولوية خلال أسبوع:
1. تضييق CSP، خصوصًا `frameSrc` و`scriptSrc`.
2. تحويل استثناءات CSRF من بادئات عامة إلى مسارات دقيقة.
3. تحديث الاعتماديات ذات الثغرات أو عزلها.
4. إضافة سجل تدقيق عند أي تغيير في `content` يتضمن روابط جديدة.

الأولوية خلال شهر:
1. إضافة اختبار أمني للمحتوى: يمنع `javascript:`, `data:`, روابط خارجية غير مصرح بها، وiframes غير موثوقة.
2. إضافة لوحة “روابط خارجية في المقالات” للمدققين.
3. تنظيف قاعدة البيانات الحالية بسكربت dry-run يعرض كل الروابط الخارجية داخل المقالات قبل أي تعديل.

## استعلامات مفيدة لفحص قاعدة البيانات

ينفذ هذا على نسخة قراءة أو نسخة احتياطية أولًا:

```sql
SELECT id, title, slug,
       regexp_matches(content, 'href=["'']([^"'']+)["'']', 'gi') AS link
FROM articles
WHERE content ~* 'href=["'']https?://';
```

```sql
SELECT id, title, slug
FROM articles
WHERE content ~* '(javascript:|data:text/html|onerror=|onclick=|<script|<iframe)';
```

## قرار أمني مقترح

اعتبر المقالات HTML غير موثوق حتى لو جاءت من محرر. اسمح فقط بما يحتاجه المقال الصحفي فعلًا، واجعل الروابط الخارجية استثناءً مرئيًا ومدققًا، وليس جزءًا عاديًا من أي محتوى محفوظ.
