# نموذج تشغيل Codex Security في «سبق»

> الحالة: تجربة تقريرية غير حاجبة للدمج. لا توجد إصلاحات آلية.

## الهدف

يضيف `Codex Security` مراجعة سياقية لتغييرات Pull Requests مع الإبقاء على
Gitleaks وSemgrep و`npm audit`. لا يغيّر الفحص بناء التطبيق أو النشر أو سلوك
الويب وiOS وAndroid والـAPI.

## التفعيل الآمن

1. أضف GitHub Actions secret باسم `CODEX_SECURITY_API_KEY` بمفتاح مخصص للفحص.
2. أضف repository variable باسم `CODEX_SECURITY_ENABLED` وقيمته `true`.
3. اختياريًا اضبط `CODEX_SECURITY_MAX_COST_USD`؛ القيمة الافتراضية `5` دولارات
   للفحص، وهي حد تقديري وليست سقف فوترة صارمًا.

يبقى الـjob متوقفًا ما لم تكن `CODEX_SECURITY_ENABLED=true`. يعمل فقط على PR
داخلي موثوق، ويتجاوز fork PRs وDependabot. لا تستخدم `pull_request_target` مع
مفتاح الفحص.

نتائج الفحص خاصة وقد تحتوي مقتطفات من الشفرة وتفاصيل استغلال. تُحفظ كـartifact
لمدة ثلاثة أيام فقط، ولا تُرفع إلى SARIF ما دام GitHub Code Security غير مفعّل
للمستودع الخاص.

## سياسة الإصلاح: أثر سير العمل أولًا

مخرجات الفحص مرشّحات تحتاج تحققًا، وليست تصريحًا بتعديل الكود. يمنع تشغيل
`codex-security patch` داخل CI أو دمج إصلاح مولّد آليًا دون المراحل التالية:

1. **التحقق من النتيجة:** إثبات مسار بيانات أو وصول قابل للتنفيذ، وتسجيل سبب
   النتيجة الصحيحة أو الإيجابية الكاذبة.
2. **تحديد مالك النظام:** مطابقة الملفات مع `docs/systems/registry.json`، ثم
   قراءة `docs/systems/<id>/SYSTEM.md` قبل التعديل.
3. **تتبّع سير العمل:** توثيق السلسلة من نقطة الدخول إلى auth/RBAC والخدمة
   والتخزين أو التكامل الخارجي، ثم جميع المستدعين والوظائف الخلفية المتأثرة.
4. **فحص المنصات:** تحديد أثر الويب وiOS وAndroid صراحة. تغييرات API أو `shared/`
   تُعامل كتغيير عابر للمنصات وفق `AGENTS.md`.
5. **التوافق:** توثيق ما إذا كان الإصلاح يغيّر payload أو status code أو session
   أو cookie أو صلاحية أو webhook أو cache أو rate limit أو retry/failover.
6. **التحقق السلبي والإيجابي:** اختبار منع الاستغلال مع الحفاظ على التدفق
   الشرعي. تشمل الخطة unit/integration، واختبار المستهلك الفعلي عند الحاجة.
7. **النشر والتراجع:** تحديد المراقبة بعد النشر وإشارة الفشل وطريقة التراجع،
   خصوصًا لمسارات Cloudflare Pages/Railway والجلسات والتخزين.
8. **PR محدود:** إصلاح واحد أو نظام واحد قدر الإمكان. أي مشكلة جانبية تذهب إلى
   Issue أو PR منفصل.

لا تنتقل النتيجة إلى «جاهزة للإصلاح» قبل وجود ملخص مكتوب لهذه النقاط في Issue
أو وصف PR.

## مراحل الاعتماد

### المرحلة 1 — Advisory

- فحص diff لكل PR داخلي.
- لا يوجد `--fail-on-severity`.
- مراجعة الدقة والتغطية والتكلفة والمدة.
- لا إصلاحات آلية ولا رفع SARIF.

### المرحلة 2 — Baseline

- فحص يدوي للمسارات الأعلى خطورة باستخدام `docs/security/threat_model.md`.
- قسّم الفحص حسب نظام أو حد أمني صغير؛ لا تفحص `server/` والمستودع كاملًا في
  تشغيل واحد.
- تصنيف النتائج إلى: مؤكدة، إيجابية كاذبة، خطر مقبول، أو تحتاج معلومات.
- إنشاء أعمال إصلاح منفصلة بعد تقييم أثر سير العمل.

أظهر التشغيل التجريبي بتاريخ 2026-07-29 أن جمع `server` و`functions` و`web-next`
و`shared` في فحص واحد تجاوز حد التكلفة التقديري قبل إنتاج تقرير مختوم. كما أن
فحص ثمانية ملفات أمنية معًا وصل إلى الحد قبل الإغلاق. لذلك تُجرى الفحوصات
الأساسية اللاحقة على حدود أصغر (نظام واحد أو تدفق واحد)، ولا تُعامل المخرجات
الجزئية كقائمة نتائج أو كدليل على سلامة النطاق.

### المرحلة 3 — Merge gate

- لا تبدأ قبل استقرار الدقة والتكلفة وإغلاق backlog المؤكد.
- أضف `--fail-on-severity high` لفحص PR فقط.
- فشل التغطية الجزئية أو المجهولة يبقى فشلًا يحتاج مراجعة، لا يُتجاهل.

## التحقق من الإصلاح

بعد أي إصلاح:

1. شغّل اختبارات النظام والمستهلكين المحددة في تقييم الأثر.
2. أعد `codex-security validate` على النتيجة الأصلية عند توفرها.
3. أعد فحص diff وتحقق من `coverage.json`، ولا تعتبر غياب النتيجة وحده دليلًا
   على نجاح الإصلاح.
4. سجّل ما تغير في السلوك، وما بقي ثابتًا، وكيف يمكن التراجع.
